# Governance Rules (Universal Edition)

This file is the single authority for prohibitive hard rules and the mechanical assertions (AMA). SKILL.md's "Prohibited Constraints" section keeps a condensed summary and points here. Sub-agent delegation rules are in §3 of this file; judgment thresholds and confidence tiers in `judgment-parameters.md`; output self-check in `validation-checklist.md`.

## Prohibited Constraints (HARD RULES, highest priority)

> **Agent Mechanical Assertion (AMA, priority higher than all items below)**
> Items 1-18 below are "abstract prohibitions" describing "what should be done"; during execution an AI may "gloss over" them after understanding. The following 5 are **mechanically checkable hard assertions** — each can be verified by "counting/comparing" with no ambiguity and no reliance on interpretation. If any AMA assertion fails, the conclusion is directly invalid, regardless of whether the AI "thinks it did it right".
>
> **AMA-1 Column-count assertion**: every penetration/UV/DAU detail table's data-column count MUST == time-window day count (daily granularity: 30 days = 30 columns; weekly = week count). Any table with only "first/last columns / a few columns" = violation. Check method: count the header date columns, do not rely on "feels detailed enough".
>
> **AMA-2 Full-traversal assertion**: the candidate drill-down combination count quoted in step 2 MUST == the full-set count of suspect-dimension × remaining splittable dimensions; after finishing, every quoted combination must have an "executed" or "user-reduced" record. Reconcile numerically: `quoted count == processed count`. One short = missed full traversal.
>
> **AMA-3 Item-by-item checkbox assertion**: when Part 3 completes, you MUST output the "all-dimension breakdown status table" (a visible table, not a mental note), with every cell except N/A marked ✓. Any ✗ or "table not output" = treated as not fully broken down; may not say "all/every dimension".
>
> **AMA-4 Daily-series assertion**: any group judged "normal (no trend change)" or "anomalous (has trend change)" must base the judgment on the **full N-day intra-group rate series**, not the first/last two points. If a group's judgment can only be derived from "first-day vs last-day two numbers" (cannot produce intermediate dates), that judgment does not hold.
>
> **AMA-5 Quote-list assertion (step 2a)**: before calling AskUserQuestion, the main agent MUST have output, **within the same reply**, the "candidate-combination list" — `suspect dimension × {remaining splittable dimensions}` listed line by line, each line with an incrementing number, ending with a fixed "total N groups". Mechanical check: ① the number of numbered items in the list == N (total combinations); ② the number of AskUserQuestion options == N, each option mapping one-to-one with each list line (label = combination name); ③ options must NOT be "which suspect dimension to drill" style (suspect dimensions are decided in step 1b, not asked here).
> Any of the three unsatisfied = step 2a incomplete = drilling forbidden; must complete the list first, then ask. Do NOT "ask first then fill list", "ask only suspect dimension without listing combinations", "list without numbers/count".

0. **Do NOT run analysis without product config** — event names, field names, table names must be read from the product config (`configs/product-config-*.md`); do NOT guess (e.g., default an entry-event name / default `hive.ta.v_event_*`). First use must fill the product config template; later reuse the persisted config. **Project ID and time range are required; if the user did not provide them, you MUST first ask via AskUserQuestion, do NOT list projects yourself, search events, or default a project for the user** (the only allowed helper action: when the user explicitly says "help me find the project", list candidates for the user to choose — do NOT self-select)
1. **Do NOT show only first/last 2 days in a dimension-breakdown table** — must include N date columns (N = time-window day count)
2. **Do NOT skip Part 4 step 2a's user confirmation and drill down directly** — must first output the "candidate-combination list" (numbered + counted, see AMA-5), then call AskUserQuestion and wait for the reply. **Asking the wrong object also counts as skipping**: AskUserQuestion may only ask "which remaining dimensions to cross with the suspect dimension" (option = each cross combination, multiSelect); do NOT ask "which suspect dimension to drill" (that is already decided in step 1b, not asked here)

> **2b. Do NOT merge two confirmations (HARD RULE)** — Part 4 has two decision points, each requiring an independent confirmation; do NOT merge into one question, do NOT omit the first:
> - **First (step 1b close)**: after the main agent determines the "anomaly-dimension candidate list", it MUST **first present it to the user** (with suspect-level distinction: true trend change vs follows aggregate, each group's intra-group rate trend, judgment rationale), **wait for the user to confirm "which suspect dimensions to drill"**, then enter step 2a.
> - **Second (step 2a)**: based on the confirmed suspect dimensions, list the full "suspect dimension × remaining splittable dimensions" candidate-combination list (numbered + counted, no recommendation), then ask which to cross.
> - Violation forms: ① merging "which dimensions are suspect" and "which dimensions to cross" into one AskUserQuestion; ② the main agent not presenting the candidate list and deciding the drill object for the user (i.e., skipping the first confirmation); ③ in step 1b presenting the candidate list without distinguishing "true trend" vs "follows aggregate", marking all groups' synchronous decline as anomalous; ④ **step 1b only reporting dimension names / only giving multiples, without attaching concrete data** — the user cannot see the sub-agent's detail; must replay the aggregate reference value + each suspect dimension's groups "first/last rate → Δpp" + suspect-level comparison multiple. The judgment action and judgment basis must appear in the same reply.
> - Key distinction: **1b recommends the "drill object" (wants opinion, may recommend); 2a does not recommend the "cross combination" (wants full enumeration, no recommendation)** — two different decision points; do NOT apply one side's rule to the other.
3. **Do NOT delegate user-interaction steps to sub-agents** — AskUserQuestion/ExitPlanMode etc. must be executed by the main agent. Part 4 step 2a, data-caliber confirmation, and product-config confirmation all fall here
4. **Do NOT use first/last difference in place of full trend for the "change" column** — change must be computed from the full N-day data
5. **Do NOT treat MUST phrasing as optional** — anything marked MUST must be executed
6. **Do NOT skip the confirmation step after AskUserQuestion fails** — fall back to plain-text questioning; do not skip
7. **Do NOT attribute version-volume decline directly to "version migration"** — "volume dropped because it migrated" is an inevitability, not a root cause. Before concluding "version migration / iteration transition", you MUST first falsify version defect: **prefer "same-cohort before/after upgrade comparison"; if unavailable, use new vs old version same-period intra-group penetration comparison (intra-group difference <2pp AND the decline fully explained by share change → pure structural migration); otherwise you MUST run "version-difference diagnosis" to dig into the version's own problem**
8. **Do NOT silently overwrite existing conclusions in multi-round analysis** — multi-round progression (e.g., 30d → 7d) is **incremental** by default; overriding requires explicit authorization ("recompute/redo/overturn"). Before incremental analysis, you MUST bring the prior root cause's **suspect dimension** into this round's Part 3/4 mandatory checks to verify it still holds in the latest data; on conflict, confirm with the user first rather than silently replacing.
9. **Do NOT treat "between-group difference" as "time-trend fluctuation"** — between-group difference (e.g., iOS consistently above Android, new version consistently above old) is a static cross-section feature, not the "fluctuation" this skill attributes. Inflection/shape/type-1-5 judgments target only "change over time". With no aggregate inflection, any dimension's between-group difference (no matter how large or in what direction) does NOT constitute "fluctuation"; do NOT force the version-defect/structural-migration framework, and do NOT fabricate "early-bird effect"/"normal range" to smooth it over — list the data honestly. **Before saying "this is a static between-group difference", ask group-by-group "did this group's own rate change over time?"; only when the intra-group rate change over time < trend-inflection dual threshold may you archive it as static difference. Between-group difference and "a group itself is falling" can coexist; they are not mutually exclusive; do NOT use "between-group difference is normal" to cover up intra-group time-trend.**
10. **Do NOT label any dimension "core dimension"** — version, OS, new/old, organic/paid, channel, country/region, entry-source are **equally important**, none default-prioritized. Whether "core" is decided by data (which dimension shows significant time-trend change), not by fixed labels.
11. **Do NOT conclude after a single drill-down** — dimension drill-down is **recursive**: any dimension showing significant time trend must be treated as a "bucket" and further cross-drilled by other **splittable** dimensions, until (a) all groups in the bucket move in sync AND have been verified by ≥2 orthogonal splits (confirmed whole-dimension problem; **convergence threshold in SKILL.md "whole-dimension early convergence", do NOT close with only 1 orthogonal dimension drilled as "whole-dimension"**), or (b) an atomic dimension is reached (event property / user property has no finer split). **Do NOT use fixed mappings to preset stop points, and do NOT preset "which dimension to drill by default" — candidate drill-down = suspect dimension × {all remaining splittable dimensions} full set, executed one by one, no fixed combination; only (a) or (b) allows stopping.** "What to drill" is decided by "which splittable dimensions remain", not preset or hardcoded.
12. **Do NOT conclude "confirmatory" style without checking residual signals** — type judgment (Part 5) is confirmatory, but before concluding you MUST do one falsification: re-run the suspect dimension's intra-group rate by the "next un-split dimension" to confirm no residual signal where "a subgroup's change direction is opposite to the primary attribution, or magnitude far exceeds it". If a residual signal exists, the attribution is invalid — return to Part 4 to continue drilling; do NOT fall back to the old conclusion. "Aggregate rate flat" ≠ "intra-group rates flat"; when the aggregate is +0.16pp healthy, some subgroup's intra-group rate may already have crashed 5pp.
13. **Do NOT reuse the old conclusion when incremental trend accelerates** — in incremental analysis, if the new window's key-metric change magnitude ≥ 1.5× the previous window, treat as trend acceleration; do NOT directly reuse the prior round's root-cause type; must run the new window's full drill-down (Part 4 recursion + Part 5 residual-signal check) before concluding.
14. **Do NOT silently down-sample/up-sample granularity** — granularity is the user-confirmed highest-priority constraint; once locked (daily/weekly) it applies throughout: inflection judgment, trend shape, Part 3 breakdown, Part 4 drill-down **all only use the confirmed granularity**. If the user chose daily, do NOT fold back to weekly mean/weekly weighting for trend comparison (weekly mean erases mid-segment inflections, reading accelerating decline as flat slight decline); only when weekly is chosen may you aggregate.
15. **Do NOT judge "structural dilution" from first/last share only** — type 4a (low-penetration group share rising) requires the low-penetration group's share to be **monotonically rising**. Before concluding 4a, you MUST check the group's share **full daily series direction**: if the share "rose then fell" or has turned downward, structural dilution does not hold and you may not attribute to 4a; at this point, if the group's intra-group rate is still independently falling, it should be judged "endogenous deterioration" (type 1), not structural dilution. Share trend and intra-group rate trend must be viewed **separately**; do NOT compare only the first/last two share values.
16. **Do NOT enter Part 4 with incomplete Part 3 dimension breakdown** — all dimension breakdowns (incl. entry-source independent breakdown) must be **queried all at once** and each run through anomaly judgment before concluding "all dimensions". Entry-source is an independent breakdown; do NOT query only one and claim "entry-source broken down". **The conclusion "all/every dimension moved in sync" may only be output after every dimension is queried and anomaly-judged**; concluding "all" after querying half = conclusion invalid.
17. **Do NOT "query but not output"** — every detail table actually queried (Part 1 aggregate trend, Part 3 each dimension's numerator UV/denominator DAU/penetration, Part 4 each cross drill-down combination, Part 5 supply side) must be **fully output item-by-item** in the report with the full window's daily/weekly data columns (matching query granularity). Do NOT compress daily detail into "first/last two columns + difference" summary; do NOT give conclusion without detail. Query granularity = output granularity must not be broken.
18. **Do NOT guess on supply side / environment layer** — supply shrinking, product-traffic downgrade, algorithm-match failure etc. must hit the SKILL.md "high-frequency root-cause library" evidence combination (none missing) before judging. Judging "supply shrinking" from just "online room count dropped" = violation; must simultaneously satisfy "entry rate unchanged" etc.

## Sub-Agent Delegation Rules

> **Core principle: distinguish "computation" from "judgment".** Computation (querying data, applying formulas, computing daily series) may be delegated to sub-agents; judgment ("which dimensions are anomalous", "what is the root cause" conclusions) + any user interaction MUST be executed by the main agent. What cannot be delegated is not "what was computed" but "what conclusion was drawn".

### Must be executed by the main agent (do NOT bundle-delegate)

| Step | Reason |
|------|------|
| Part 0 product-config confirmation (AskUserQuestion) | requires user interaction |
| Data-caliber confirmation before Part 3 (AskUserQuestion) | requires user interaction |
| Part 4 step 2a drill-direction confirmation (AskUserQuestion) | requires user interaction |
| **Part 4 step 1b: the "anomaly-dimension list" judgment conclusion** | the judgment conclusion directly determines step 2a's MUST phrasing. If delegated to a sub-agent, the sub-agent may skip step 2a's user confirmation (it cannot call AskUserQuestion), violating HARD RULE #2 |
| Any step requiring AskUserQuestion/ExitPlanMode | sub-agents cannot call interaction tools |

### Delegatable to sub-agents

| Step | Note |
|------|------|
| Part 1 aggregate-trend query | pure query, no judgment |
| Part 3 multi-dimension breakdown query | pure query, no judgment |
| **Part 4 step 1a: per-dimension intra-group daily series computation + dual-threshold mechanical calculation** | pure data processing, no judgment, no interaction. Note: only delegate "computation", not the "which dimensions are anomalous" conclusion (that conclusion belongs to step 1b, main agent) |
| Part 4 step 2b cross drill-down SQL execution | direction already confirmed by main agent; sub-agent only executes queries |
| Part 3/4/5 data organization and computation | data processing, no user interaction |

> **Step 1a / step 1b split line**: the sub-agent returns "each dimension's groups' intra-group rate daily series + whether each crossed the dual threshold raw computation result" (data); the main agent judges "which dimensions are anomalous, forming the anomaly-dimension list" (conclusion), then takes that conclusion to step 2a to ask the user. Data is delegatable, conclusion is not.

### Delegation SOP (key to saving tokens, MUST)

> Data querying + parsing is the token-cost bulk of this task (30 days × N dimensions × M cross drill-downs, multi-file 100KB+ JSON returns). **Delegating to sub-agents = these detail data stay in the sub-agent's context; the main agent only receives "conclusions"** — tokens saved by more than half. Follow this SOP:

1. **Delegation boundary**: the sub-agent may only do "Part 1 aggregate query + Part 3 dimension queries + intra-group penetration daily-series computation + dual-threshold application". The sub-agent uses `scripts/ae_query.sh` (query) and `scripts/dim_analyzer.py --summary-only` (compute) to narrow output, then returns "each dimension's each group: first/last rate / Δ / crossed threshold / consecutive-direction cumulative" this **conclusion-level** text, **without returning daily detail**.

2. **Prompt essentials for the sub-agent**: state clearly ① environment precondition (`ae-cli config current` to confirm login target host) ② product-config key items (project_id, event table, event names, field names) ③ use heredoc to write SQL (do NOT hand-escape quotes) ④ `--summary-only` to narrow output ⑤ return only conclusion lines + key numbers, not daily detail ⑥ add `LOWER()`/`--os-normalize` for OS, `--min-dau 200 --top 20` for version.

3. **What the main agent receives**: a "machine-readable conclusion list" (e.g., `new user: 27.36%→21.19% Δ-6.17pp net -5.25pp hint ★anomaly; old user: -2.08pp net +0.08pp; OS: Android -2.76 / iOS -1.72; …`). The main agent does step 1b judgment + step 2a question from this, **without re-opening raw JSON**. Note: `dim_analyzer.py`'s ★ mark means the authoritative dual threshold was crossed; the separate `hint` label means the first-half/second-half displacement also exceeded the configured noise band. Both are mechanical results, not the final anomaly verdict — the main agent must still confirm the full daily-series shape (consecutive decline / V-shape / inversion) before judging a dimension anomalous.

4. **When to pull detail back to the main agent**: only when the main agent judges a dimension "anomalous" and needs cross drill-down or residual-signal check, pull that dimension's daily detail back to the main agent (or re-delegate). Healthy dimensions' daily data (no time-trend change) **do not enter the main context**.

5. **Anti-pattern (forbidden)**: the main agent running ae-cli one by one, dumping all files into its own context, then parsing itself — that is the token bulk and unnecessary.

6. **【MUST·multi-agent parallel split; do NOT stuff all dimensions into a single sub-agent】** Part 3's full dimension breakdown **must NOT be bundled to one sub-agent running serially**. A single agent serially running 20+ ae-cli queries, each waiting on the data engine with no progress feedback, looks "stuck" to the user and gets manually interrupted — the task aborts. Correct approach: **split by dimension across multiple sub-agents running in parallel**. Balanced 3-way example:
   - Agent A: OS + new/old user + app version (pure SQL join, serial fast)
   - Agent B: organic/paid + channel + country/region (event model + SQL mixed)
   - Agent C: entry source (event-model-heavy, largest result)

   **Concurrency-cap iron rule**: because ae-cli has a per-host concurrency cap, **the parallel sub-agent cap is 3**. 2 is insufficient parallelism; 4-5 will fire SQL across agents simultaneously and trigger `CONCURRENCY_LIMIT_EXCEEDED`. Each agent runs its own dimension group **serially** internally (6-8 queries), cross-agent naturally staggered, concurrency-safe. If dimension count is not a multiple of 3 or one query is particularly heavy, adjust equivalently by "3 items per agent", but never exceed the 3-agent cap and never stuff more than 3-4 dimensions into one agent.

7. **Sub-agent prompts must hardcode the window boundary**: a precise interval like `[2026-08-08, 2026-09-06]` must be explicitly hardcoded in every sub-agent prompt, and stress that the event model's `previous value>N` returns one extra day and must be filtered by date range. Omitting this causes window-caliber drift between agents.

8. **Sub-agent prompts must attach product-config key items**: project_id, event table, user table, event names, field names all hardcoded in the prompt; do NOT let the sub-agent "guess" or "query" the config — the sub-agent has no context to read the product-config file; guessing the event name = the entire batch of queries is wasted.
