# Scope Definition Guide

## 0. 引用规范（Citation Rules）

本指南中的所有引用，必须使用统一的显式文档引用格式，不得保留临时引用占位符或不统一的文档名写法。

### 0.1 中文引用格式
- 文档名统一写为：`文档名.md`
- 推荐句式统一写为：
  - 见 `文档名.md` 中关于”主题”的说明。
- 如果无法精确到主题，则写为：
  - 见 `文档名.md`。

### 0.2 禁止使用的引用形式
以下形式不得出现在本指南中：
- `:contentReference[...]`
- `oaicite`
- 《文档名》
- 其他无法在 skill 运行时被正式解析的临时引用标记

### 0.3 引用使用原则
- 当前实现层的第一证据始终是已定位对象的 SQL / query / dashboard / report 配置。
- 产品说明文档用于定义层解释、规则校验与边界条件说明。
- 文档引用不能替代 SQL 事实。
- 若当前实现与产品定义不一致，必须分开说明：
  - 当前实现是怎样的
  - 产品定义通常是怎样的

### 0.4 引用维护要求
- 本指南每次修改后，应检查是否残留临时引用占位符。
- 若有残留，必须在正式使用前全部替换为显式文档引用。
- 不允许将无法映射到实际资源的引用保留在最终版本中。

## 1. 目标（Objective）

本指南用于帮助执行体与客户对齐分析口径。

本指南的目标不是让执行体在第一次回复时，就把所有口径细节全部展开。  
相反，执行体应先输出一个**足够具体、可供确认**的口径版本，再主动询问客户是否需要继续下钻到更细的定义层。

本指南适用于以下分析资产与分析对象：
- SQL
- query / qp / adhoc_query
- dashboard / report
- 指标
- 事件
- 事件属性
- 用户属性
- 虚拟事件
- 虚拟属性
- 维度表属性
- 标签
- 分群
- 分组项
- 时间范围 / 时间粒度
- 筛选逻辑
- 阶段值
- 计算方法

其中，事件表和用户表是分析可用的底层数据，事件属性和用户属性可直接用于筛选和分组；系统中还存在虚拟事件、虚拟属性和维度表属性等派生分析资产。见 `data-management-events-and-properties.md` 中关于“事件、事件属性、用户属性”的说明，以及 `virtual-properties-and-dimension-table-properties.md` 中关于“虚拟属性和维度表属性”的说明。

另外，**口径对齐应优先基于已定位的具体分析对象进行**。  
这里的“已定位对象”通常指：
- project_id
- dashboard_id
- report_id
- 或可直接定位到对象的 SQL / qp / adhoc_query
- 或之前生成的分析结果原文 / 截图 / 链接

如果客户尚未提供足以定位对象的信息，执行体的第一步不是直接给出高确定性的口径结论，而是先请求这些定位信息。

## 2. 核心原则（Core Principle）

始终遵循以下顺序：

**customer-provided object info / SQL first → MCP-assisted retrieval second → SQL-first → reference-validated → customer-confirmed**

并遵循以下输出策略：

**先中后细（Layered Scope Depth）**

也就是：
1. 先优先向客户请求并定位具体分析对象；
2. 若客户无法提供完整信息，再通过 MCP 工具补充收集对象与查询条件；
3. 再从 SQL / query / dashboard 中提取当前实现口径；
4. 再结合产品 reference 文档验证其定义语义；
5. 先给客户一个中等粒度的口径说明；
6. 再由执行体主动询问客户，是否需要继续对齐到更细的层级。

默认情况下，不要一次性展开所有标签 / 分群 / 虚拟属性 / 维度表属性 / 版本 / 时区 / 更新方式细节。  
只有在客户需要，或当前结果与客户理解不一致时，才继续下钻。

另外，本产品查询与表达式统一按 **Trino 语法** 理解；虚拟属性也基于 Trino SQL 表达式创建。见 `virtual-properties-and-dimension-table-properties.md` 中关于“虚拟属性表达式”的说明，以及 `creating-virtual-properties-best-practices.md` 中关于“Trino 表达式与虚拟属性使用方式”的说明。

## 3. 口径分层策略（Scope Depth Strategy）

执行体在做口径对齐时，不应默认一次性展开所有定义细节，而应采用**动态分层、逐层请示**的方式推进。

每进入下一层之前，必须完成以下三个动作：
1. **确认当前层级是否已满足客户**
2. **预告下一层还可以继续对齐哪些更细的口径**
3. **明确请求客户补充哪些信息，以及这些信息通常可以从哪里获得**

### L1：当前实现层（默认层）
默认先对齐“当前这条 SQL / 这个 query / 这个报表到底是怎么统计的”。

这一层应优先说明：
- 当前统计对象是什么
- 当前统计范围是什么
- 当前使用了哪些筛选
- 当前按哪些维度分组
- 当前时间范围、时间粒度、计算方式是什么
- 当前标签 / 分群 / 虚拟属性 / 维度表属性在本次分析中是如何被使用的

这一层的目标是：  
让客户先确认“当前实现口径”是否正确，而不是立刻进入对象本身的定义细节。

### L1 结束后的必做动作
L1 输出后，执行体必须主动请示客户是否已经满足其需求。

同时，执行体需要预告：  
如果继续进入 L2，还可以进一步对齐哪些内容，例如：
- 标签 / 分群属于哪一类
- 虚拟属性是如何派生出来的
- 维度表属性是如何补充出来的
- 分析主体是什么
- 结算时区是什么
- 是否为预计算结果
- 是否存在版本口径差异

并说明如果客户希望继续，需要补充哪些信息，例如：
- 对象名称
- 对象类型（如果知道）
- 定义 SQL
- 配置截图
- 来源报表 / query / 看板 ID
- 文档关键词

同时加入固定请示：

> 当前这个逻辑是否符合你想要的业务口径？

### L2：定义解释层（按需展开）
只有在客户明确表示 L1 不足时，才进入 L2。

这一层的目标是：  
解释“当前分析里使用到的标签 / 分群 / 虚拟属性 / 维度表属性本身是怎么来的”。

L2 应优先说明：
- 对象属于哪一类
- 该对象本身如何定义
- 分析主体是什么
- 结算时区是什么
- 更新方式是什么
- 是否为预计算结果
- 是否涉及日期版本 / 动态匹配
- 该对象表达的业务语义到底是什么

### L2 结束后的必做动作
L2 输出后，执行体仍必须再次请示客户是否已满足需求。

同时，执行体需要预告：  
如果继续进入 L3，还可以进一步对齐哪些更细的规则，例如：
- 条件标签 / 条件分群的布尔逻辑
- 行为序列规则
- 时间窗口
- 关联属性
- 未做过事件
- SQL 标签 / SQL 分群 / 虚拟属性的定义 SQL
- 历史版本、用户历史数据、结果来源等细节
- 虚拟属性表达式的真实业务语义
- 粒度是否一致

并明确请求客户补充所需信息，例如：
- 条件配置截图
- 定义 SQL
- 标签版本使用方式
- 分群来源结果
- 虚拟属性规则
- 维度表结构
- 具体想核对的口径点

同时加入固定请示：

> 当前这个逻辑是否符合你想要的业务口径？

### L3：细节校验层（仅在必要时）
只有在客户明确要求确认细节规则，或当前结论依赖这些规则时，才进入这一层。

这一层的目标是：  
校验复杂规则、历史口径、边界条件，以及定义层中的潜在误差来源。

只有在以下情况才进入这一层：
- 客户明确要求确认标签 / 分群 / 虚拟属性 / 维度表属性定义细节
- 客户怀疑对象本身定义有问题
- 当前 SQL 使用层和产品定义层疑似冲突
- 历史版本 / 动态匹配 / 结算时区 / 更新方式会影响结论
- 当前对象是 SQL 标签 / SQL 分群，需要直接查看其定义 SQL
- 当前对象是条件标签 / 条件分群，且需要继续核对行为序列、时间窗口、关联属性、未做过事件等复杂规则
- 当前对象是虚拟属性，且其表达式语义、粒度、字段来源或派生类型会影响结果理解

### 默认策略
如果客户没有明确要求细到定义层，执行体应默认停留在 L1。  
如果客户没有明确要求进入 L3，执行体在 L2 后应先请示，而不能自动继续展开。

## 4. 证据优先级（Evidence Priority）

当口径存在歧义时，按以下优先级判断：

1. **已定位的具体分析对象及其 SQL / query / dashboard 配置中的显式实现逻辑**
2. **产品 reference 文档**
3. **TE 既定产品行为**
4. **客户自然语言中的预期**

注意：
- 客户表述是确认目标，不是默认事实。
- 如果当前实现与产品定义不一致，必须明确分开说明。
- 不要把“当前 SQL 怎么写”与“产品标准语义是什么”混为一谈。
- 如果某个定义层判断依赖推测而非明确证据，必须明确告诉客户这是推测。
- **如果尚未定位到具体 project / dashboard / report / query / SQL，则当前只能做初步解释或泛化说明，不应给出高确定性的口径结论。**

## 5. 默认工作流（Default Workflow）

### Step 0：优先向客户请求对象定位信息与 SQL
在开始口径对齐前，执行体应优先向客户请求能定位分析对象的信息，尤其是：
- project_id
- dashboard_id
- report_id
- SQL 查询条件

如果客户能直接提供 SQL 查询条件，则可优先基于 SQL 对齐口径。  
如果客户无法提供 SQL，但能提供 project / dashboard / report 信息，则可据此继续定位对象。  
如果客户既无法提供 SQL，也无法完整提供对象定位信息，执行体才尝试通过 MCP 工具补查对应的 qp、adhoc_query 或相关配置。

如果对象仍未定位成功：
- 执行体不应直接给出高确定性的口径结论
- 而应先说明当前只能做初步解释
- 并请求客户补充 project_id、dashboard_id、report_id，或 SQL / query / 既有分析结果

### Step 1：识别客户当前要对齐到哪一层
先判断客户要的是：
- 只确认当前查询 / 报表怎么统计
- 还是继续确认标签 / 分群 / 虚拟属性 / 维度表属性本身怎么定义
- 还是继续确认版本、时区、更新时点等更细口径

如果客户没有明确说明，默认先输出 **L1 当前实现层**。

### Step 2：先提取当前实现口径
从 SQL / query 中提取：
- 数据来源
- 统计对象
- 事件范围
- 时间范围
- 时间粒度
- 筛选结构
- 分组结构
- 计算方法
- 特殊处理
- 输出结构

### Step 3：条件触发地做更细检查
若在短时间内可判断，则进一步检查：
- 关键字段属于哪类来源
- 粒度是否一致
- 虚拟属性表达式在业务上到底表达什么

若短时间内无法判断：
- 先不要强行深挖
- 先向客户请示是否需要做如此细的口径对齐
- 若客户愿意，再请求客户补充对象来源或配置
- 若客户不能补充，再做更细致检查
- 若最终仍只能依赖推测，则在输出中明确写明“这是推测”

### Step 4：输出一版“足够确认”的当前口径
先用业务语言告诉客户：
- 当前到底在统计什么
- 在什么范围内统计
- 用了什么筛选
- 按什么维度拆分
- 标签 / 分群 / 虚拟属性 / 维度表属性在这里是怎么被使用的

### Step 5：主动追问是否继续下钻
在第一轮说明后，执行体必须主动询问客户是否需要继续展开。例如：
- 你是只想确认当前查询怎么筛、怎么分组、怎么统计？
- 还是还想确认这个标签 / 分群 / 虚拟属性 / 维度表属性本身的定义？
- 是否需要继续对齐到版本、时区、更新方式这一级？
- 当前这个逻辑是否符合你想要的业务口径？

如果客户不熟产品，应优先用简单的话语提出这些问题。  
必要时，再补充术语解释，并告诉客户可以去搜哪些关键词，例如：
- 虚拟属性
- 维度表属性
- 标签
- 分群
- 时区
- 日期版本

### Step 6：按需进入更细层级
只有客户明确需要，或当前理解存在差异时，才继续展开 L2 / L3。  
若继续展开前还缺少信息，执行体应先说明缺口，再请求客户补充，而不是直接假设定义层结论。

## 6. SQL 解析检查清单（SQL Parsing Checklist）

不能只看部分 SQL 就解释口径。  
必须完整检查：子查询、join、派生字段、where/filter、group by、聚合逻辑和输出结构。

### 6.1 数据来源
识别：
- 来源表
- 事件表 / 用户表 / 派生表
- 是否 join 了汇率表、映射表、标签 / 分群结果表、维表等

要回答的问题：
- 结果基于哪类数据源？
- 当前结果是事件级、用户级、记录级还是金额级？

### 6.2 统计对象
识别真正的统计对象：
- 事件次数
- 去重用户数
- 属性值
- 金额
- 人均值
- 阶段值
- 列表型结果
- 布尔型结果
- 其他聚合结果

不能只根据指标名称猜。

### 6.3 事件范围
识别：
- 统计了哪些事件
- 排除了哪些事件
- 是单事件还是多事件集合
- 是否是公式型对象

### 6.4 时间范围与时间粒度
识别：
- 分区过滤时间
- 真实业务事件时间
- 展示时区 / 时区偏移逻辑
- 聚合粒度（天 / 周 / 月 / 原始时间）
- 是否涉及阶段窗口完整性

规则：
- 不能把分区过滤直接当成最终业务时间范围。
- 必须区分性能层分区裁剪和业务层统计时间。
- 如果时间已经偏移到展示时区，应按展示时区解释业务时间。
- 如果涉及阶段值，必须检查是否排除了不完整数据。
- 若对象依赖事件属性上的“时区”标注，应注意该属性可能是时区偏移计算依据。见 `filtering-data-through-filtering-conditions.md` 中关于“时间型事件属性与时区偏移”的说明。

### 6.5 筛选结构
识别：
- 事件属性筛选
- 用户属性筛选
- 标签筛选
- 分群筛选
- 虚拟属性筛选
- 维度表属性筛选
- 条件关系（AND / OR）
- 筛选作用范围（全局 / 局部）
- 是否存在相对时间、相对事件时间、对象组筛选

解释规则：
- 筛选决定的是**哪些数据被纳入计算**。见 `filtering-data-through-filtering-conditions.md` 中关于“筛选决定纳入数据范围”的说明。
- 不能把筛选和分组混淆。
- 时间型事件属性会偏移到展示时区后再比较。见 `filtering-data-through-filtering-conditions.md` 中关于“时间型事件属性时区偏移”的说明。
- 时间型用户属性和用户标签不会偏移。见 `filtering-data-through-filtering-conditions.md` 中关于“用户属性与用户标签时间处理”的说明。
- 相对事件发生时刻中的“天(相对)”是 24 小时，不是自然日。见 `filtering-data-through-filtering-conditions.md` 中关于“相对时间”的说明。
- 如果多个并列条件存在，必须解释它们是 AND 还是 OR。见 `filtering-data-through-filtering-conditions.md` 中关于“条件关系”的说明。
- 如果筛选只作用于某个指标或公式的一部分，不能把它说成全局口径。见 `filtering-data-through-filtering-conditions.md` 中关于“全局 / 局部筛选”的说明。

### 6.6 分组结构
识别：
- 分组字段来源
- 单分组还是交叉分组
- 数值分桶 / 时间分组 / 列表分组方式
- 是否使用标签 / 分群 / 虚拟属性 / 维度表属性做分组

解释规则：
- 分组决定的是**结果如何拆开对比**。见 `comparing-analysis-through-grouping-items.md` 中关于“分组用于结果对比拆分”的说明。
- 不能把分组和筛选混淆。
- 多个分组维度会形成交叉粒度结果。见 `comparing-analysis-through-grouping-items.md` 中关于“多分组 / 交叉分析”的说明。

#### 数值型分组
判断是否是：
- 默认区间
- 离散数字
- 自定义区间

重要规则：
- 默认区间可能根据分组值数量自动切换为 12 个区间；
- 自定义区间是左闭右开。见 `comparing-analysis-through-grouping-items.md` 中关于“数值型分组区间规则”的说明。

#### 时间型分组
判断是否是：
- 按选定粒度汇总
- 不汇总，直接按实际上报时间分组

不能只写“按时间分组”，必须说明是：
- 按天 / 周 / 月等粒度汇总
- 还是按原始时间逐值分组。见 `comparing-analysis-through-grouping-items.md` 中关于“时间分组”的说明。

#### 列表型分组
判断是否是：
- 按元素
- 按列表整体
- 按元素集合

重要规则：
- 按元素：一条记录可能参与多个分组；
- 按列表整体：顺序和重复都可能有意义；
- 按元素集合：先去重排序，再按集合分组。见 `comparing-analysis-through-grouping-items.md` 中关于“列表型分组”的说明。

### 6.7 计算方法
识别准确的计算方式。

#### 基础预置方法
- 总次数
- 触发用户数
- 人均次数

重要规则：
- 总次数是事件次数。见 `calculation-method-logic-explanation.md` 中关于“总次数”的说明。
- 触发用户数是去重用户数。见 `calculation-method-logic-explanation.md` 中关于“触发用户数”的说明。
- 人均次数 = 总次数 / 触发用户数。见 `calculation-method-logic-explanation.md` 中关于“人均次数”的说明。

#### 数值型属性方法
判断是否为：
- 均值
- 人均值
- 中位数
- N 分位数
- 方差
- 标准差

重要规则：
- 均值 = 属性值总和 / 属性值个数。见 `calculation-method-logic-explanation.md` 中关于“均值”的说明。
- 人均值 = 属性值总和 / 触发用户数。见 `calculation-method-logic-explanation.md` 中关于“人均值”的说明。
- 中位数是位置统计，不是平均值。见 `calculation-method-logic-explanation.md` 中关于“中位数”的说明。
- 分位数反映分布位置，不是均值。见 `calculation-method-logic-explanation.md` 中关于“分位数”的说明。
- 方差 / 标准差反映波动，不是中心水平。见 `calculation-method-logic-explanation.md` 中关于“方差 / 标准差”的说明。

#### 列表型属性方法
判断是否为：
- 列表去重数
- 集合去重数
- 元素去重数

重要规则：
- 列表整体去重 ≠ 集合去重。见 `calculation-method-logic-explanation.md` 中关于“列表去重 / 集合去重”的说明。
- 集合去重不区分顺序和重复。见 `calculation-method-logic-explanation.md` 中关于“集合去重”的说明。
- 元素去重统计的是所有列表里的不同元素。见 `calculation-method-logic-explanation.md` 中关于“元素去重”的说明。

#### 布尔型属性方法
判断是否为：
- 为真数
- 为假数
- 为空数
- 不为空数

重要规则：
- 这些默认是事件次数口径，除非 SQL 明确改成用户级。见 `calculation-method-logic-explanation.md` 中关于“布尔型属性计数”的说明。

### 6.8 阶段值逻辑
如果 query 或 report 中涉及留存 / 分布分析阶段值，执行体必须校验阶段值解释。

重要规则：
- 阶段值是一段时间内的汇总，不是单日值。见 `stage-value-logic-explanation.md` 中关于“阶段值不是单日值”的说明。
- 人数类指标通常默认是阶段总和。见 `stage-value-logic-explanation.md` 中关于“人数类阶段总和”的说明。
- 率类指标通常默认是加权平均，不是每日率的简单平均。见 `stage-value-logic-explanation.md` 中关于“率类加权平均”的说明。
- 同时展示指标可能根据计算方法和公式形态采用不同逻辑。见 `stage-value-logic-explanation.md` 中关于“同时展示指标逻辑”的说明。
- 不完整数据会被排除。见 `stage-value-logic-explanation.md` 中关于“不完整数据排除”的说明。

除非有明确依据，不能把阶段值解释成“简单平均”。

### 6.9 特殊处理
识别：
- 时区偏移
- 币种换算
- null 处理
- 非有限值过滤
- 去重
- lookup / 映射 join
- 局部公式逻辑
- 阶段窗口完整性过滤
- 类型转换
- 时间戳转换
- 字符截取
- 联合去重
- 常数构造

### 6.10 输出结构
识别：
- 输出是明细还是聚合
- 是否分组
- 是否同时输出序列和总值
- 是否是阶段值、原始值或分组结果

### 6.11 字段来源类型检查（条件触发）
当能够在短时间内判断时，执行体应尽量识别每个关键字段属于哪类来源：
- 原始事件属性
- 原始用户属性
- 虚拟事件属性
- 虚拟用户属性
- 维度表属性
- 标签结果字段
- 分群结果字段
- 其他 lookup / 映射字段

如果短时间内无法判断：
- 不强制深入
- 先请示客户是否需要对齐到这一层
- 若客户不能提供来源信息，再尝试细查或推测
- 若最终是推测，必须明示

### 6.12 粒度一致性检查（条件触发）
当能够在短时间内判断时，执行体应检查：
- 事件级字段与用户级字段是否被混合使用
- 当前表达式是在判断“事件是否满足条件”还是“用户是否具备状态”
- 当前 distinct key 是否等于客户口中的“人数 / 用户数 / 主体数”

如果短时间内无法判断：
- 先请示客户是否需要继续对齐到这一层
- 若客户不能补充信息，再细查
- 若最终只能推测，必须在输出中明示

### 6.13 虚拟属性表达式语义检查（条件触发）
当关键字段是虚拟属性时，若有必要，执行体应检查它更像属于哪类表达式语义：
- 计算型
- 类型转换型
- 时间转换型
- 字符截取型
- 拼接型
- 条件判断型
- 常数型
- 维表补充型

并进一步判断，它在业务上表达的是：
- 事件级条件
- 用户级状态
- 主体级映射
- 去重键
- 分组键
- 时间辅助字段
- 其他派生语义

若无法快速判断，应向客户请示是否要继续对齐到这一层。

## 7. 标签、分群、虚拟属性、维度表属性的使用层解释（Usage Layer）

### 7.1 标签与分群
在分析执行层，标签和分群都可以先抽象理解为一类“主体 -> 标记结果”的派生资产：

- 第一列：分析主体
- 第二列：标记结果

其中：
- 标签更像：`分析主体 -> 标签值`
- 分群更像：`分析主体 -> 是否属于该分群`

因此，在 L1 层，执行体不必一开始就展开标签 / 分群本身的定义，而应先说明：
- 当前查询用了哪个标签 / 分群
- 它在当前查询里是被用于筛选还是分组
- 它对应的是哪个分析主体
- 它对当前统计结果的影响是什么

标签本质上是给主体打标记；分群本质上是选出一个主体集合。见 `user-tags.md` 中关于“标签”的说明，以及 `user-cohorts.md` 中关于“分群”的说明。

### 7.2 虚拟属性
在使用层，可以先把虚拟属性理解为：
- 像在事件表或用户表中新增加了一列派生字段

虚拟属性可由事件属性、用户属性、用户标签等通过 Trino 表达式二次计算得到，可用于筛选、分组或辅助计算。见 `virtual-properties-and-dimension-table-properties.md` 中关于“虚拟属性”的说明，以及 `creating-virtual-properties-best-practices.md` 中关于“虚拟属性表达式”的说明。

因此，在 L1 层，执行体应先说明：
- 当前查询用了哪个虚拟属性
- 它是在筛选、分组还是计算中使用
- 它更像事件级字段还是用户级字段
- 当前表达式更像在判断什么

### 7.3 维度表属性
在使用层，可以先把维度表属性理解为：
- 基于某个键型属性关联维度表后，自动补充出来的业务信息列

维度表属性可以作为事件属性或用户属性参与分析。见 `virtual-properties-and-dimension-table-properties.md` 中关于“维度表属性”的说明。

因此，在 L1 层，执行体应先说明：
- 当前用了哪个维度表属性
- 它是基于哪个键型属性补充出来的
- 它在当前查询中用于筛选、分组还是解释结果

## 8. 标签与分群的定义层下钻规则（Definition Layer）

当客户需要继续确认标签 / 分群本身的定义口径时，执行体再从使用层进入定义层。

### 8.1 什么时候进入定义层
仅在以下情况继续展开：
- 客户明确问“这个标签 / 分群是怎么定义的”
- 客户怀疑当前结果与自己理解不一致
- 当前分析结论高度依赖标签 / 分群定义
- 当前结果涉及历史版本 / 动态匹配 / 结算时区 / 更新方式
- 当前对象是 SQL 标签 / SQL 分群
- 当前对象是条件标签 / 条件分群，且客户需要确认其复杂规则

### 8.2 进入定义层前的必做动作
进入定义层前，执行体必须先说明：
1. 当前只能确定“标签 / 分群在本查询中的使用方式”
2. 若继续进入定义层，还可以对齐哪些内容
3. 需要客户补充哪些信息，以及这些信息通常可以从哪里获得

例如：
- 若是 SQL 标签 / SQL 分群，需要定义 SQL，可从标签/分群配置页或创建人处获取
- 若是条件标签 / 条件分群，需要条件配置截图，可从产品配置页面获取
- 若是结果分群，需要来源报表 / query / 看板信息
- 若涉及历史版本，需要版本使用方式或版本日期信息

### 8.3 标签定义层需要确认什么
若继续确认标签定义，至少需要确认：
- 标签类型
- 标签分析主体
- 标签结算时区
- 标签更新与预计算方式
- 标签版本
- 条件 / 首末次 / 指标值标签的进一步规则。对应规则见 `user-tags.md`、`conditional-first-last-metric-value-tags.md`、`date-versions-of-tags.md`。

#### 标签类型
- ID 标签
- 条件标签
- 首末次标签
- 指标值标签
- SQL 标签。见 `user-tags.md` 中关于“标签类型”的说明，以及 `conditional-first-last-metric-value-tags.md` 中关于“条件 / 首末次 / 指标值标签”的说明。

#### 标签分析主体
标签结果中的“人数”不是天然用户数，而是标签分析主体的数量，例如 `#user_id`、`#account_id`、`#distinct_id` 等。见 `user-tags.md` 中关于“分析主体”的说明。

#### 标签结算时区
若标签定义使用事件数据，则事件时间按标签结算时区判断；分析时切换展示时区不会重算标签结果。见 `user-tags.md` 中关于“标签结算时区”的说明。

#### 标签更新与预计算
标签是预计算型数据，不是每次使用时即席计算。其结果会受自动更新、手动更新、创建/编辑计算等方式影响。见 `user-tags.md` 中关于“更新方式与预计算”的说明。

#### 标签版本
数据条件型标签的标签值可能随每次计算变化；分析历史数据时，需要确认使用的是最新版本、动态匹配还是某个历史版本。见 `date-versions-of-tags.md` 中关于“标签日期版本”的说明。

#### 条件 / 首末次 / 指标值标签的进一步细节
- 条件标签：需确认条件类型、布尔组合、标签值优先顺序、是否涉及行为序列。见 `conditional-first-last-metric-value-tags.md` 中关于“条件标签”的说明。
- 首末次标签：需确认取首次还是末次、取哪个属性值、属性值为空时是否无法打标。见 `conditional-first-last-metric-value-tags.md` 中关于“首末次标签”的说明。
- 指标值标签：需确认时段、属性、聚合方式、是否使用公式，以及公式不可计算时的处理。见 `conditional-first-last-metric-value-tags.md` 中关于“指标值标签”的说明。

### 8.4 分群定义层需要确认什么
若继续确认分群定义，至少需要确认：
- 分群类型
- 分群来源
- 分群分析主体
- 分群结算时区
- 分群更新与预计算方式
- 条件分群的进一步规则。对应规则见 `user-cohorts.md`、`conditional-cohorts.md`。

#### 分群类型
- ID 分群
- 结果分群
- 条件分群
- SQL 分群。见 `user-cohorts.md` 中关于“分群类型”的说明。

#### 分群来源
如果是结果分群，应继续追溯它来源于哪个分析结果、哪个“人数类结果”。见 `user-cohorts.md` 中关于“结果分群来源”的说明。

#### 分群分析主体
分群“人数”也是分析主体数量，不天然等于用户数。见 `user-cohorts.md` 中关于“分析主体”的说明。

#### 分群结算时区
条件分群 / SQL 分群若使用事件数据，则时间条件按分群结算时区判断；分析展示时区变化不会重算分群结果。见 `user-cohorts.md` 中关于“分群结算时区”的说明。

#### 分群更新与预计算
分群是预计算型数据，可能通过定时、手动、跟随计算、系统触发、创建计算、编辑计算等方式更新。见 `user-cohorts.md` 中关于“更新方式与预计算”的说明。

#### 条件分群的进一步细节
如果是条件分群，且客户希望继续确认规则，则要进一步确认：
- 条件类型（做过 / 未做过 / 依次做过 / 未依次做过 / 属性满足）
- 条件逻辑如何组合
- 行为序列是否严格顺序
- 所有步骤是否都落在时间范围内
- 是否存在关联属性
- 是否存在步骤间未做过事件
- 时间窗口是否按 24 小时计算
- 是否命中特殊序列情形。见 `conditional-cohorts.md` 中关于“条件类型、序列、时间窗口、关联属性、未做过事件”的说明。

### 8.5 SQL 标签 / SQL 分群的处理规则
如果客户要求确认 SQL 标签 / SQL 分群的定义口径，而当前对话中没有提供其定义 SQL，则执行体应明确说明：
- 当前只能解释它在本查询中的使用方式
- 若要继续确认其定义口径，需要客户补充定义 SQL 或规则配置截图

执行体不应在没有定义 SQL 的情况下，自行推断 SQL 标签 / SQL 分群的定义逻辑。

### 8.6 虚拟属性定义层
若继续确认虚拟属性定义，至少需要确认：
- 这是虚拟用户属性还是虚拟事件属性
- 它的表达式规则是什么
- 依赖哪些原始字段 / 标签 / 属性
- 其数据类型是什么
- 它是在筛选、分组还是计算里被使用
- 它表达的业务语义是什么
- 它更接近事件级条件还是用户级状态
- 是否涉及类型转换失败置空、时间转换、联合去重、条件判断等情况。见 `virtual-properties-and-dimension-table-properties.md` 中关于“虚拟属性类型与字段依赖”的说明，以及 `creating-virtual-properties-best-practices.md` 中关于“表达式语义与常见误区”的说明。

### 8.7 维度表属性定义层
若继续确认维度表属性定义，至少需要确认：
- 它依赖哪个原始键型属性
- 维度表主键与原属性类型是否匹配
- 当前补充的是显示名还是业务信息
- 它是否来自列表 / 时间 / 文本 / 数值 / 布尔类型属性
- 是否存在对象 / 对象组不可直接挂维度表等约束。见 `virtual-properties-and-dimension-table-properties.md` 中关于“维度表属性”的说明。

### 8.8 SQL 标签 / SQL 分群 / 复杂虚拟属性的规则
如果客户要求确认 SQL 标签 / SQL 分群 / 复杂虚拟属性的定义口径，而当前对话中没有提供其定义 SQL 或规则配置，则执行体应明确说明：
- 当前只能解释它在本查询中的使用方式
- 若要继续确认其定义口径，需要客户补充定义 SQL 或规则配置截图

执行体不应在没有定义 SQL 的情况下，自行推断其定义逻辑。

## 9. 条件型标签 / 分群的进一步规则（仅在需要时展开）

### 9.1 条件标签
条件标签支持：
- 做过
- 未做过
- 属性满足
- 行为序列条件。见 `conditional-first-last-metric-value-tags.md` 中关于“条件标签”的说明。

一个标签下可以有多个标签值，但一个主体只能命中唯一标签值，并按标签值顺序优先匹配。见 `conditional-first-last-metric-value-tags.md` 中关于“标签值优先顺序”的说明。

### 9.2 首末次标签
首末次标签的标签值来自首次/末次目标行为发生时的属性值，而不是时段聚合值。若所取属性为空，则无法得到标签值。时间型属性按标签时区偏移后的值取值。见 `conditional-first-last-metric-value-tags.md` 中关于“首末次标签”的说明。

### 9.3 指标值标签
指标值标签的标签值来自指定时段内的属性聚合结果，也支持公式型定义。若公式中部分事件未参与，则未参与部分按 0；若公式不可计算（如除数为 0），则无法打标。见 `conditional-first-last-metric-value-tags.md` 中关于“指标值标签”的说明。

### 9.4 条件分群
条件分群支持：
- 做过
- 未做过
- 依次做过
- 未依次做过
- 属性满足。见 `conditional-cohorts.md` 中关于“条件类型”的说明。

条件分群的条件组合不是简单平铺，而是同类条件先组合，再连接不同大类的逻辑结果。见 `conditional-cohorts.md` 中关于“条件组合方式”的说明。

### 9.5 序列型条件分群
如果是依次做过 / 未依次做过，则还需确认：
- 顺序是否严格
- 所有步骤是否都在时间范围内
- 是否存在关联属性
- 是否存在步骤间未做过事件
- 时间窗口中的“天”是否按 24 小时判断
- 是否命中特殊情形（重复事件、虚拟事件、未做过与步骤事件重叠）。见 `conditional-cohorts.md` 中关于“行为序列与时间窗口”的说明。

## 11. 面向客户的默认输出模板（Default Output Template）

执行体的默认输出应遵循“先中后细”的结构，并在复杂背景下尽量做到：
- 先给结论
- 再给依据
- 再给待确认项
- 表达顺序清晰，避免把筛选、分组、计算方式、对象定义混在一起

### 11.0 当对象尚未定位时的默认处理
如果客户还没有给出足以定位分析对象的信息，执行体应先向客户请求定位信息，而不是直接给出高确定性的口径结论。

优先向客户请求：
- project_id
- dashboard_id
- report_id
- SQL 查询条件

如果客户没有这些信息，则可进一步请求：
- qp / adhoc_query
- 之前生成的输出原文
- 报表 / 看板链接或截图

如果客户暂时无法提供完整信息，执行体才可尝试通过 MCP 工具补充收集对应的 query、adhoc_query 或配置结果。

推荐话术：

> 为了准确对齐口径，我需要先定位你说的是哪个分析对象。  
> 你可以优先给我：
> - project_id
> - dashboard_id
> - report_id
> - 或这份分析对应的 SQL 查询条件
>
> 如果你手头没有这些，也可以先发报表 / 看板链接、截图，或者之前生成的输出原文。  
> 如果这些都暂时没有，我再尝试通过系统里的工具补查对应信息。  
> 在对象没有定位清楚前，我只能先给你初步解释，不能当作最终口径确认。

### 第一轮默认输出（L1）
建议按以下顺序组织：

#### A. 当前在统计什么
- 统计对象
- 指标含义
- 统计主体

#### B. 当前统计范围是什么
- 事件范围
- 时间范围
- 时间粒度

#### C. 当前有哪些限制条件
- 筛选条件
- 是否使用了标签 / 分群 / 虚拟属性 / 维度表属性 / 属性限制
- 条件是全局还是局部

#### D. 当前结果如何拆分
- 分组维度
- 对象在这里是用于筛选还是分组

#### E. 当前如何计算
- count / distinct count / sum / avg / stage value 等
- 是否有特殊处理（时区 / 汇率 / 去重 / 无效值过滤 / 表达式派生等）

#### F. 当前仍未展开的部分
- 当前是否尚未展开对象本身的定义
- 当前是否尚未展开版本 / 时区 / 更新方式等定义层信息

#### G. 若发现口径可能与客户预期不一致
要直接指出，例如：
- 当前这个逻辑更像在判断什么
- 不完全等于客户口中的哪个业务状态
- 请客户确认这是否符合预期

例如可用模板：

> 当前这个逻辑更像是在判断 **[当前实现语义]**，  
> 而不完全等于 **[客户自然语言预期]**。  
> 当前这个逻辑是否符合你想要的业务口径？

### 第一轮输出后的固定追问
第一轮说明后，执行体必须主动请示客户是否已满足需求，并同时完成：
1. 确认当前层级是否已足够
2. 预告下一层可继续对齐的内容
3. 请求客户补充继续下钻所需的信息

推荐固定话术：

> 我先对齐的是“这个查询 / 报表当前怎么筛、怎么分组、怎么统计”。  
> 这一级如果已经满足你的问题，我就先停在这里。  
> 如果你希望，我还可以继续帮你对齐更细的内容，例如：
> - 这个标签 / 分群 / 虚拟属性 / 维度表属性本身属于哪一类
> - 它是怎么定义出来的
> - 它的分析主体、结算时区、更新方式、版本口径是什么
>
> 如果你想继续下钻，请告诉我你最想进一步确认哪一项；  
> 若是 SQL 标签 / SQL 分群 / 复杂虚拟属性，请补充定义 SQL；  
> 若是条件型对象，请补充配置截图或规则说明；  
> 若是结果分群，请补充来源报表 / query / 看板信息。

### 第二轮输出（L2）
如果客户选择继续确认定义层，则第二轮再补充：
- 对象类型
- 分析主体
- 结算时区
- 更新方式
- 是否预计算
- 日期版本 / 动态匹配
- 是否需要补充定义 SQL / 规则配置

第二轮结束后，仍要再次请示客户是否继续进入更细层，并预告：
- 还能继续核对哪些更细规则
- 还需要补充哪些材料

### 第三轮输出（L3）
如果客户继续要求更细校验，则第三轮再展开：
- 条件标签 / 条件分群的布尔逻辑
- 序列规则
- 时间窗口
- 关联属性
- 特殊边界条件
- 历史版本 / 用户历史数据 / 结果来源等复杂细节
- 虚拟属性表达式语义
- 粒度一致性问题

### 长对话 / 高 token 消耗场景
如果对话太长，回溯历史成本过高，应请求客户补充：
- 之前分析结果的提示
- 或原文
- 或相关 SQL / query / 报表截图

并明确说明是为了避免基于不完整上下文误判。

## 12. 常见误区（Common Pitfalls）

- 不要默认一次性把所有细节都讲完
- 不要把标签和分群混为一谈
- 不要把对象当前使用方式误当成其定义方式
- 不要把展示时区误当成标签 / 分群结算时区
- 不要把刷新结果页误当成重算对象
- 不要把分区过滤直接当成业务时间范围
- 不要把阶段值默认解释成简单平均
- 不要把相对天数 / 时间窗口天数当自然日
- 不要把虚拟属性的表达式结果直接当成客户口中的业务状态
- 不要忽略事件级字段与用户级字段混用可能导致的语义偏差
- 不要在缺少定义 SQL / 配置时假装已经知道复杂对象的定义逻辑
- 不要在未定位具体分析对象时，就给出高确定性的最终口径结论

## 13. 完成标准（Completion Standard）

### 如果目标是 L1
必须明确：
- 统计对象
- 统计范围
- 筛选
- 分组
- 时间口径
- 计算方式
- 标签 / 分群 / 虚拟属性 / 维度表属性在当前查询中的使用方式
- 当前逻辑是否符合客户想要的业务口径（若有疑义则必须请示）

### 如果目标是 L2 / L3
还必须明确：
- 对象类型
- 分析主体
- 结算时区
- 更新方式
- 是否为预计算
- 是否使用日期版本 / 动态匹配
- 是否需要查看定义 SQL / 规则配置
- 若有关键判断依赖推测，必须明确写出“这是推测”
