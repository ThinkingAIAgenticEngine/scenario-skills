## 1. 能力元信息（Capability Metadata）

这一部分回答三个问题：
1. 这是什么能力
2. 解决什么问题
3. 在什么情况下启用

### 1.1 能力名称
- 名称：`analysis-scope-alignment`

### 1.2 用途说明（Purpose）

- 这个能力用于：
  - 基于**已定位的具体分析对象**，确认当前分析结果、看板、报表、query、SQL 或既有 agent 输出的统计口径；
  - 将当前口径用客户能理解的方式表达出来，并与客户进行讨论和确认；
  - 与客户确认当前口径是否符合其业务理解与分析目标；
  - 在客户需要时，进一步下钻标签、分群、虚拟属性、维度表属性、时间、筛选、分组、计算方式、版本、时区等定义层口径；
  - 在口径确认后，为后续调整 SQL、修改分析方案、重建分析逻辑或生成分析报告提供明确输入。

- 主要解决的问题：
  - 让客户理解目前的看板 / 报表 / query / agent 生成物的分析结果到底是按什么口径统计出来的；
  - 确认当前输出物的口径是否与客户理解一致；
  - 判断当前口径是否真正对应客户想问的问题；
  - 当当前口径与客户预期不一致时，帮助识别差异点，并继续讨论更合适的新口径；
  - 在涉及标签、分群、虚拟属性、维度表属性、复杂筛选、复杂分组、阶段值、计算方法时，避免客户把“当前实现语义”误当成“业务定义语义”；
  - 在继续生成报告、改写 SQL、调整分析逻辑前，先完成口径确认，避免在错误定义上继续分析。

- 适用对象：
  - 客户在当前 ae-cli 或当前对话上下文中有权限访问的分析对象，包括：
    - 项目
    - 看板
    - 报表
    - SQL 查询
    - query / adhoc_query / qp
    - 标签
    - 分组项
    - 指标
    - 既有分析结论或历史对话中产出的分析结果
  - 当前对话中客户提供的 SQL 查询条件、截图、链接、既有 agent 输出；
  - 与分析口径有关的事件、事件属性、用户属性、虚拟事件、虚拟属性、维度表属性、标签、分群、分组项、筛选、时间粒度、阶段值和计算方法。

### 1.3 适用场景（When to Use）

- 当用户希望：
  - 对齐某个看板、报表、指标、标签、分组项、query 或分析结果的统计口径；
  - 讲解分析结果含义；
  - 解释某个分析结果“是如何算出来的”；
  - 确认某个结果中“用户群是谁、如何进入统计范围、如何被排除”；
  - 验证数据来源与定义，例如确认某个标签、分群、虚拟属性、维度表属性在当前分析中的含义；
  - 核对不同报表、不同查询、不同分析结果之间的口径差异；
  - 判断当前结果是否已经回答了客户真正的问题；
  - 在生成分析报告、继续分析、重写 SQL、提出优化建议前，先确认当前口径；
  - 讨论“当前口径是否满足业务问题”，并明确需要调整的定义点。

- 典型场景：
  - “请帮我对齐这个看板的计算口径”
  - “告诉我这个分析的用户群是哪些人”
  - “这个标签人群的结果是什么意思”
  - “帮我看一下这两个报表为什么指标不一样”
  - “请解释这个 query / 报表现在是怎么筛、怎么分组、怎么统计的”
  - “检查并对齐 XXX 指标在不同报表间的计算差异”
  - “先别出报告，先帮我确认口径对不对”
  - “这个留存到底是按什么规则算的”
  - “这个标签值是怎么定义出来的”
  - “这个虚拟属性筛出来的人是不是我想要的人”
  - “这个分群和这个标签在这里分别起了什么作用”
  - “生成分析报告前，先帮我确认当前口径”

- 不建议直接用在：
  - 纯结果润色或纯文案改写任务；
  - 不涉及口径确认的通用报告生成；
  - 无分析对象、无定义对象、无结果上下文的泛泛业务咨询。

- 应识别的意图要点：
  - **定位信息及分析对象**
    - project_id
    - dashboard_id
    - report_id
    - qp / adhoc_query
    - SQL 查询条件
    - 之前 agent 输出的原文 / 截图 / 链接
  - **指标 / 功能名**
    - 如 DAU、留存、ARPU、标签值、分群、阶段值、虚拟属性等
  - **范围对象**
    - 单个看板 / 单个报表 / 单个 query
    - 多个看板 / 多个报表之间的对比
    - 标签 / 分群 / 虚拟属性 / 维度表属性 / 指标 / 分组项 / 筛选项
  - **时间口径**
    - 按日 / 周 / 月
    - 指定日期区间
    - 展示时区 / 结算时区 / 版本时间
  - **对齐目标**
    - 只确认当前实现口径
    - 继续确认定义层口径
    - 继续确认细节规则 / 边界条件
  - **优先级 / 允许改动**
    - 默认先做解释与确认
    - 如需改写，仅限分析层 / SQL 层调整
    - 坚决不允许对底层库表数据做出任何改动

### 1.4 触发入口（Entry Points）

- 通过什么方式触发：
  - 客户自然语言请求；
  - 客户给出 project_id / dashboard_id / report_id 后请求解释口径；
  - 客户给出 SQL，或 agent 从 ae-cli 命令中获取 query / adhoc_query 条件后，请求解释当前统计逻辑；
  - 客户引用之前 agent 生成的分析结果，并要求解释或确认口径；
  - agent 主动询问客户是否需要对齐 / 讲解分析口径，在得到肯定答复后触发；
  - 在生成分析报告、改写 SQL、重建分析逻辑前，系统或执行流程判断需要先确认口径；
  - 用户询问标签定义、分组项定义、时间粒度、时间范围、过滤条件、阶段值汇总方式、计算方法；
  - 用户明确输入固定命令 `scope-alignment`
    - 当输入这个字段时，skill 必须被调动；
    - 然后先确认客户想对齐的是哪个对象：如 project、dashboard、report、query、SQL、标签、分群、虚拟属性、指标等；
  - 当对话进入“结果是否符合预期”的讨论阶段时，优先触发本能力以先完成口径确认；
  - 若用户提问的是标签、分群、虚拟属性、维度表属性等对象，但当前尚未绑定到具体分析对象，本能力仍可触发，用于：
    - 做初步解释；
    - 尝试定位对象；
    - 或明确说明当前只能停留在对象通识 / 使用层解释，尚不能当作具体口径确认结论。

- 触发信号：
  - **出现某类关键词**
    - 口径
    - 粒度
    - 标签定义
    - 分群定义
    - 虚拟属性
    - 维度表属性
    - 分组项
    - 计算方法
    - 阶段值
    - 汇总方式
    - 时区
    - 版本
    - 统计逻辑
    - 时间范围
    - 时间粒度
    - 留存
    - DAU
    - ARPU
    - 标签值
    - 人群定义
    - “这批人是谁”
    - “这个结果是什么意思”
  - **涉及某类操作**
    - 制作标签
    - 选择分群
    - 选择虚拟属性
    - 选择维度表属性
    - 选择分组项
    - 选择时间粒度
    - 讨论分析结果是否符合预期
    - 生成分析报告前确认统计口径
  - **输入对象包含**
    - SQL
    - query / qp / adhoc_query
    - dashboard / report / panel
    - 标签名
    - 分组项名
    - 指标名
  - **出现以下高风险语义时应优先触发**
    - 客户把一个技术字段当成业务状态来理解
    - 客户把标签 / 分群 / 虚拟属性的当前使用方式，当成其定义方式
    - 客户问“这是不是我想要的人 / 指标 / 留存 / 付费用户”
    - 客户问“为什么这个结果和我想的不一样”
  - **用户意图包含**
    - “解释这个结果”
    - “确认定义”
    - “比较两个结果为什么不同”
    - “在继续分析前先确认口径”
  - **触发边界补充**
    - 若当前问题涉及标签、分群、虚拟属性、维度表属性等对象，但缺少具体分析对象上下文，本能力仍可以触发；
    - 但此时默认目标应为：
      - 初步解释；
      - 对象定位尝试；
      - 或提示当前还不能完成高确定性的具体口径确认；
    - 不应在缺少具体对象上下文时，伪装成已经完成了某个具体报表 / query / SQL 的口径对齐。

- 操作边界：
  - **允许**
    - 解释当前口径
    - 对比当前口径与客户期望
    - 提出新的统计口径建议
    - 给出新的 SQL 查询语句或新的查询逻辑建议
  - **坚决不允许**
    - 对底层库表数据做任何直接修改
    - 在未完成口径确认前直接把客户期望当成既定事实写入分析结论

### 1.5 前置条件（Prerequisites）

- 在开始正式口径对齐前，必须优先尝试定位分析对象。
- 若客户手头方便，可优先提供：
  - project_id
  - dashboard_id
  - report_id
  - SQL 查询条件
- 如果客户无法提供完整信息，或无法明确说明对象上下文，则应通过 ae-cli 命令补查：
  - qp
  - adhoc_query
  - 相关配置或对象信息
- 如果对象尚未定位成功：
  - agent 只能给出初步解释或泛化说明；
  - 不应输出高确定性的最终口径结论；
  - 必须明确说明当前仍缺少对象定位信息。

### 1.6 默认触发后的首要动作（First Action After Trigger）

- 先确认客户要对齐的是哪个具体分析对象。
- 若客户手头方便，可优先提供：
  - project_id
  - dashboard_id
  - report_id
  - SQL 查询条件
- 如果客户能直接提供 SQL，则优先基于 SQL 解释当前实现口径；
- 如果客户无法提供完整对象信息，则通过系统工具定位具体 query / adhoc_query / 相关配置；
- 如果客户提供的是之前 agent 输出的分析结果，则先基于原文、截图、链接或相关 SQL 尝试定位对象；
- 在对象没有定位清楚前，不直接进入高确定性的定义层解释。

### 1.7 不建议触发或应谨慎触发的情况（Non-Trigger / Caution Cases）

- 客户只是做纯结果润色、纯文案改写，不涉及统计口径确认；
- 客户只是想生成一份通用报告，但不需要核对当前分析定义；
- 客户没有提供分析对象、定义对象或结果上下文，且问题只是泛泛业务咨询；
- 当前问题本质上是“新建一个分析”或“新建一个口径”，而不是解释或确认现有口径；
- 当前只能给出产品通识介绍时，不应伪装成已经完成了具体口径确认；
- 如果对象尚未定位清楚，只能做初步解释，不应输出高确定性的最终结论；
- 若问题涉及标签、分群、虚拟属性、维度表属性等对象，但尚未绑定到具体分析对象，则本能力可以谨慎触发，用于：
    - 初步解释对象含义；
    - 尝试定位对象；
    - 或说明当前只能停留在对象通识 / 使用层解释；
    - 但不应伪装成已经完成了具体报表 / query / SQL 的口径确认。

### 1.8 该能力的边界定位（Boundary Positioning）

- 这个能力的核心不是直接改 SQL，也不是直接生成报告；
- 这个能力的核心是：
  1. 先定位对象
  2. 识别当前实现口径
  3. 用客户能理解的话解释
  4. 与客户确认是否符合预期
  5. 如有必要再继续下钻或提出新口径建议

- 因此，它更适合作为这些任务的前置步骤：
  - SQL 改写
  - 新分析方案设计
  - 报告生成
  - 客户沟通
  - 结果复核

## 2. 目标与执行原则（Goal & Operating Principles）

这一部分定义该能力被触发后，agent 应按什么原则行事。

### 2.1 核心目标（Primary Goal）

- 主要目标：
  - 帮助客户基于**已定位的具体分析对象**，准确识别当前分析结果的统计口径；
  - 将当前口径用客户易于理解、可讨论、可确认的方式表达出来；
  - 与客户确认当前口径是否符合其业务问题、业务理解和分析目标；
  - 在需要时，继续下钻到标签、分群、虚拟属性、维度表属性、筛选、分组、时间、时区、版本、计算方法等定义层细节；
  - 在后续分析、SQL 改写、报告生成、逻辑重建之前，先完成口径确认。

- 次要目标：
  - 帮助客户识别“当前实现语义”和“客户期待语义”之间的差异；
  - 帮助客户识别是否需要继续下钻到 L2 / L3；
  - 在客户已有口径不满足业务问题时，协助提出可讨论的新口径方向；
  - 为后续 SQL 调整、分析重构、报告撰写提供清晰、稳定、可复用的口径输入。

- 成功标准（Success Criteria）：

  #### A. agent 可直接判断的完成标准
  - 已定位分析对象；若尚未成功定位，已明确说明仍缺少哪些定位信息；
  - 已明确说明当前解释所依据的对象或输入来源，例如：
    - project / dashboard / report
    - SQL
    - query / adhoc_query
    - 历史分析结果原文或截图
  - 已覆盖当前实现口径的关键组成部分；若信息足够，至少包括：
    - 统计对象
    - 统计范围
    - 筛选条件
    - 分组方式
    - 时间范围 / 时间粒度
    - 计算方式
  - 已明确区分：
    - 当前实现逻辑
    - 客户期望定义
  - 若存在信息不足、字段来源不明、粒度不明或定义未拿到等情况，已明确标注：
    - 待确认
    - 推测
    - 仍需客户补充的信息
  - 若需要继续下钻，已明确说明：
    - 下一层还能对齐什么
    - 还缺哪些信息
    - 建议客户提供什么材料
  - 在口径未确认前，未直接产出依赖该口径的最终分析结论、最终报告或最终 SQL 方案；
  - 在口径未确认前，未把客户期望直接写成当前既定事实。

  #### B. 需要客户反馈的确认标准
  - 客户明确表示以下之一：
    - 当前解释已经满足需求；或
    - 需要继续下钻到下一层；或
    - 当前口径不符合预期，需要进一步调整。

### 2.2 优先级原则（Priority Principles）

- 默认优先级：
  1. **先定位分析对象**
  2. **先向客户请求信息，再考虑用 ae-cli 补查**
  3. **先确认当前实现口径，再决定是否进入定义层**
  4. **先保证解释正确，再追求表达完整**
  5. **先区分已知、未知、推测，再给结论**
  6. **先确认是否满足客户问题，再进入更细粒度**
  7. **最后才考虑提出新口径或后续调整建议**

- 具体优先原则：
  - **对象定位优先于口径解释**
    - 未定位 project / dashboard / report / SQL / query 前，不应直接输出高确定性的最终口径结论。
  - **客户提供的信息优先于系统补查**
    - 应优先向客户请求：
      - project_id
      - dashboard_id
      - report_id
      - SQL 查询条件
    - 如果客户无法提供完整信息，再通过 ae-cli 命令补查 qp、adhoc_query 或相关配置。
  - **SQL 证据优先于泛化理解**
    - 若客户提供 SQL，则优先基于 SQL 解释当前实现口径。
  - **当前实现优先于定义层**
    - 先说明“现在这个结果是怎么统计出来的”，再决定是否展开“对象本身是怎么定义出来的”。
  - **确认优先于扩展**
    - 每一层解释后，都应先确认客户是否已满足，而不是自动展开全部细节。
  - **正确性优先于完整性**
    - 如果某部分暂时无法确认，应明确写成“待确认”或“推测”，而不是为了完整性强行补齐。
  - **口径确认优先于后续动作**
    - 在口径未确认前，不应直接进入：
      - 报告生成
      - SQL 改写
      - 分析结论固化
      - 优化建议定稿

### 2.3 风格要求（Style Requirements）

- 输出风格：
  - 简洁但不失逻辑；
  - 结构化；
  - 以“当前结果到底怎么得出”为主线；
  - 优先使用客户容易理解的话；
  - 只有在必要时再引入专业术语。

- 解释风格：
  - 先说当前在统计什么；
  - 再说统计范围、筛选、分组、时间和计算方式；
  - 再说当前尚未展开的定义层内容；
  - 若与客户预期不一致，要明确指出差异；
  - 每一轮都要提示客户是否继续下钻。

- 与客户沟通风格：
  - 优先用最简单的话请求信息；
  - 不默认客户熟悉产品术语；
  - 若客户对术语不熟，再补充术语解释或建议可搜索的关键词；
  - 当需要客户补充信息时，要明确告诉客户“为什么需要这些信息”；
  - 避免像审问一样连续索取系统字段，而应说明这些字段是为了准确定位对象。

- 结果表述风格：
  - 区分三类信息：
    - 已确认
    - 待确认
    - 推测
  - 不把推测写成事实；
  - 不把客户希望的口径写成当前实际口径；
  - 不把当前使用方式写成对象本身的定义方式。

### 2.4 硬性约束（Hard Constraints）

- 必须遵守：
  - 不在未定位分析对象前，输出高确定性的最终口径结论；
  - 不跳过对象定位，直接假设客户说的是某个看板 / 报表 / SQL；
  - 不在未确认上下文时做高风险推断；
  - 不把客户业务预期直接当成当前实现事实；
  - 不伪造“已确认”“已验证”“已定位”“已补查”的结论；
  - 不在信息不足时假装已经完成定义层确认；
  - 不擅自扩大任务范围，把“口径确认”直接变成“新分析设计”或“新报告输出”；
  - 不对底层库表数据做任何直接修改；
  - 不在口径未确认前，直接生成依赖该口径的最终分析结论。

- 对不确定内容的要求：
  - 对所有不确定内容，必须明确标记：
    - 这是推测
    - 这是待确认
    - 需要客户补充信息
  - 若 ae-cli 补查结果与客户提供信息存在冲突，必须回到客户确认，而不是自行替客户裁决。

### 2.5 默认行为原则（Default Operating Behaviors）

- 默认先做：
  1. 请求对象定位信息
  2. 解释当前实现口径
  3. 询问是否继续下钻

- 默认不做：
  - 不默认继续进入定义层；
  - 不默认继续进入复杂规则核查；
  - 不默认改写 SQL；
  - 不默认生成分析报告；
  - 不默认把当前口径视为正确业务口径。

- 默认在以下情况下暂停深入：
  - 对象未定位；
  - SQL 未拿到且 ae-cli 也无法可靠补查；
  - 标签 / 分群 / 虚拟属性定义 SQL 或配置缺失；
  - 粒度判断、字段来源判断只能依赖猜测；
  - 客户还没有明确需要下钻到更细层级。

### 2.6 冲突处理原则（Conflict Handling Principles）

- 当出现以下冲突时，必须显式拆开处理：
  - 客户预期 vs 当前 SQL 实现
  - 当前使用方式 vs 对象定义方式
  - 展示时区 vs 结算时区
  - 当前结果页刷新 vs 对象重算
  - 当前 query 逻辑 vs 产品标准语义
  - 客户说法 vs ae-cli 补查结果

- 处理方式：
  - 先分别陈述两边是什么；
  - 再说明当前证据更支持哪一边；
  - 若仍不能确认，明确标注“待确认”；
  - 必要时请求客户补充：
    - SQL
    - 配置截图
    - 版本使用方式
    - 看板 / 报表 / query 来源信息

### 2.7 完成时应达到的状态（Desired End State）

- agent 可感知的完成状态：
  - 已定位分析对象，或已明确说明仍缺少哪些定位信息；
  - 已解释当前实现口径的关键组成部分；
  - 已明确区分当前实现逻辑与客户期望定义；
  - 已标记待确认 / 推测部分；
  - 已说明若继续下钻，下一层还能核对什么、还缺哪些信息；
  - 已主动请求客户确认当前解释是否满足需求。

- 需要客户反馈确认的完成状态：
  - 客户明确表示当前解释已满足需求；或
  - 客户明确表示需要继续下钻；或
  - 客户明确表示当前口径不符合预期，需要调整。

## 3. 工作流与决策逻辑（Workflow）

这一部分定义该能力被触发后，agent 应按什么顺序执行，以及在不同信息条件下如何做决策。

### 3.1 总体流程（Overall Flow）

默认遵循以下流程：

1. **识别是否应触发本能力**
2. **定位分析对象**
3. **收集当前实现口径的输入材料**
4. **判断当前应停留在哪一层**
5. **提取并解释当前实现口径（L1）**
6. **每轮输出口径说明后的固定确认**
7. **请示客户是否继续下钻**
8. **按需进入定义解释层（L2）**
9. **再次进行每轮输出口径说明后的固定确认**
10. **再次请示客户是否继续下钻**
11. **按需进入细节校验层（L3）**
12. **当当前口径不符合预期时，给出推荐口径选项**
13. **沉淀可复用的口径确认结果**
14. **在口径确认后，再决定是否继续后续动作**

默认总原则：

- **customer-provided object info / SQL first**
- **ae-cli-assisted retrieval second**
- **SQL-first**
- **reference-validated**
- **customer-confirmed**

### 3.2 Step 1：识别是否应触发本能力

agent 先判断当前任务是不是“口径确认类任务”。

#### 应触发的情况
若当前请求涉及以下任一目标，应触发本能力：
- 解释某个分析结果是什么意思
- 解释某个结果是怎么统计出来的
- 对齐某个 dashboard / report / query / SQL 的统计口径
- 确认某个标签 / 分群 / 虚拟属性 / 维度表属性在当前分析中的作用
- 比较两个结果为什么不同
- 在继续分析、写报告、改 SQL 之前先确认当前口径
- 讨论当前结果是否符合客户的业务预期

#### 强制触发命令
若用户明确输入固定命令 `scope-alignment`，则本能力必须直接触发，不再做是否触发的模糊判断。

触发后默认立即进入：
1. 对象定位
2. 当前实现口径提取
3. 分层解释与确认流程

#### 不应直接触发的情况
若当前请求只是：
- 纯文案润色
- 不涉及口径的通用报告生成
- 泛泛的业务咨询
- 与具体分析对象无关的产品功能介绍

则不应直接进入完整口径确认流程。

#### 触发后的默认动作
一旦判断应触发：
- 不直接开始解释最终口径；
- 先进入 **对象定位** 步骤。

### 3.3 Step 2：定位分析对象（Object Identification）

在正式解释口径前，必须优先定位客户说的是哪个具体分析对象。

#### 客户可优先提供的信息
若客户手头方便，可优先提供：
- project_id
- dashboard_id
- report_id
- SQL 查询条件

#### 可接受的替代输入
如果客户没有上述字段，也可以接受：
- qp / adhoc_query
- dashboard / report / panel 链接
- 报表或结果截图
- 之前 agent 输出的原文
- 标签名 / 分群名 / 指标名 / 分组项名（但此时通常仍不足以独立完成定位）

#### 系统工具的使用顺序
- 优先使用客户当前已提供的信息；
- 若客户无法提供完整对象信息，再通过系统工具补查：
  - query
  - adhoc_query
  - report 配置
  - 对象相关上下文

#### 若对象仍未定位成功
如果仍无法定位：
- agent 只能给出**初步解释 / 泛化说明**
- 必须明确说明当前仍缺少哪些对象定位信息
- 不应输出高确定性的最终口径结论
- 不应进入高确定性的定义层判断

### 3.4 Step 3：收集当前实现口径所需材料（Evidence Collection）

对象定位后，agent 需要收集能解释当前实现口径的直接材料。

#### 优先级
1. 客户直接提供的 SQL
2. 已定位对象对应的 query / adhoc_query / report 配置
3. 当前对话中已有的分析结果、截图、原文
4. reference 文档
5. 产品既定行为知识

#### 要收集的材料类型
- SQL 查询条件
- query / qp / adhoc_query
- dashboard / report 配置
- 当前结果截图或原始输出
- 标签 / 分群 / 虚拟属性 / 维度表属性名称
- 客户当前最关心的问题点

#### 收集后应立即判断
- 当前材料是否足够解释 L1；
- 当前材料是否不足以进入定义层；
- 当前是否需要先继续向客户请求信息。

### 3.5 Step 4：判断当前停留层级（Layer Decision）

agent 需要判断当前应该停留在哪一层：

#### L1：当前实现层
适用于：
- 客户主要想知道“这个结果现在是怎么算出来的”
- 当前目标是先解释统计对象、范围、筛选、分组、时间、计算方式
- 客户尚未明确要求解释标签 / 分群 / 虚拟属性本身的定义

#### L2：定义解释层
适用于：
- 客户明确问某个标签 / 分群 / 虚拟属性 / 维度表属性“本身是怎么定义的”
- 当前结果强依赖某个对象定义
- 客户怀疑当前结果与自己理解不一致

#### L3：细节校验层
适用于：
- 客户明确要求确认复杂规则
- 当前结论依赖复杂边界条件
- 当前对象涉及版本、动态匹配、复杂条件逻辑、序列规则、时间窗口、粒度冲突等

#### 默认原则
- 默认从 **L1** 开始；
- 只有客户明确要求，或当前结论明显依赖定义层 / 细节层时，才进入 L2 / L3。

### 3.6 Step 5：提取并解释当前实现口径（L1 Execution）

在 L1，agent 应优先解释当前实现层，而不是一开始就展开定义层。

#### 必须优先覆盖的内容
若信息足够，至少应覆盖：
- 当前统计对象是什么
- 当前统计范围是什么
- 当前筛选条件是什么
- 当前分组方式是什么
- 当前时间范围 / 时间粒度是什么
- 当前计算方式是什么
- 当前标签 / 分群 / 虚拟属性 / 维度表属性在这里是如何被使用的

#### 解释顺序建议
1. 当前在统计什么
2. 当前统计范围是什么
3. 当前有哪些筛选
4. 当前如何分组
5. 当前如何计算
6. 当前哪些定义层内容还没有展开

#### 若发现与客户预期可能不一致
应明确指出：
- 当前实现逻辑更像在判断什么
- 它不完全等于客户口中的哪个业务状态
- 请求客户确认：

> 当前这个逻辑是否符合你想要的业务口径？

### 3.6A 每轮输出口径说明后的固定动作（Per-Round Confirmation After Scope Output）

只要 agent 已经输出了一轮**口径说明**，就必须执行一次固定确认动作。

#### 固定确认动作包括
1. 确认客户是否认为当前这版口径说明已经符合预期；
2. 若不符合，确认差异主要落在哪一类问题上，例如：
   - 统计对象
   - 统计范围
   - 筛选逻辑
   - 分组方式
   - 时间口径
   - 计算方式
   - 标签 / 分群 / 虚拟属性 / 维度表属性定义
3. 确认是否需要继续下钻到下一层。

#### 适用边界
- 只有在 agent **已经输出了口径说明** 后，才执行此确认动作；
- 若当前仍停留在“对象定位阶段”或“材料收集阶段”，尚未形成口径说明，则不执行此动作。

#### 硬性要求
- agent 不应在给出口径说明后，默认客户已经认可；
- agent 不应在未确认客户是否认可前，直接把当前口径作为后续分析的既定输入。

### 3.7 Step 6：L1 后的请示（Post-L1 Confirmation）

L1 结束后，agent 必须主动请示客户，而不是自动进入下一层。

#### 必须完成的三个动作
1. 确认当前层级是否已经满足客户
2. 预告下一层还能对齐哪些内容
3. 请求继续下钻所需的信息

#### L1 后应说明的内容
例如：
- 若继续，可以解释标签 / 分群属于哪一类
- 可以解释虚拟属性 / 维度表属性是怎么来的
- 可以继续解释分析主体、结算时区、更新方式、版本口径
- 若要继续，可能需要：
  - 定义 SQL
  - 配置截图
  - 版本使用方式
  - 来源报表 / query / dashboard 信息

#### 下钻前的成本提示
若继续下钻预计会明显增加上下文消耗、历史回溯长度、材料读取量或 token 消耗，agent 应先提示客户：
- 继续下钻会更消耗上下文 / token；
- 若客户愿意继续，建议优先补充最关键的 SQL、配置截图、历史结果原文或相关片段；
- 若客户暂时不希望继续消耗太多上下文，可先停留在当前层级。

agent 不需要精确计算 token，但应在明显可能高消耗时主动提醒。

### 3.8 Step 7：进入定义解释层（L2 Execution）

只有在客户明确表示 L1 不足，或当前结论明显依赖对象定义时，才进入 L2。

#### L2 应优先解释的内容
- 对象属于哪一类
- 对象本身如何定义
- 分析主体是什么
- 结算时区是什么
- 更新方式是什么
- 是否为预计算结果
- 是否涉及版本 / 动态匹配
- 该对象表达的真实业务语义是什么

#### 对象类型包括但不限于
- 标签
- 分群
- 虚拟属性
- 维度表属性
- SQL 标签 / SQL 分群
- 条件标签 / 条件分群
- 指标值标签
- 首末次标签

#### 若信息不足
如果缺少：
- 定义 SQL
- 配置截图
- 版本信息
- 来源对象信息

则必须明确告诉客户：
- 当前只能解释其在本查询中的使用方式
- 还不能高确定性解释其定义层口径

### 3.9 Step 8：L2 后的再次请示（Post-L2 Confirmation）

L2 完成后，仍不能自动进入 L3。

#### 必须再次确认
- 当前是否已经满足客户；
- 是否还要继续核对更细规则；
- 若继续，还缺什么材料。

#### L2 后应预告的可继续核对内容
例如：
- 条件标签 / 条件分群的布尔逻辑
- 序列规则
- 时间窗口
- 关联属性
- 未做过事件
- 版本差异
- 动态匹配
- 粒度一致性
- 虚拟属性表达式语义

#### 下钻前的成本提示
若继续进入 L3 预计会明显增加上下文消耗、历史回溯长度、材料读取量或 token 消耗，agent 应再次提醒客户：
- 更细层级的核对通常更消耗上下文 / token；
- 若继续，建议优先补充最关键的定义 SQL、配置截图、历史结果片段或相关规则说明；
- 若客户暂时不希望继续消耗太多上下文，可先停留在当前层级结论。

### 3.10 Step 9：进入细节校验层（L3 Execution）

只有在客户明确要求，或当前结论依赖复杂规则时，才进入 L3。

#### L3 重点处理什么
- 复杂规则
- 边界条件
- 历史版本
- 动态匹配
- 时间窗口
- 序列逻辑
- 关联属性
- 未做过事件
- 粒度冲突
- 字段来源冲突
- 虚拟属性表达式语义冲突

#### L3 的工作要求
- 只能在证据足够时下高确定性判断；
- 若仍有不确定项，必须明确标为：
  - 推测
  - 待确认
- 若当前判断需要更多定义材料，必须回到客户请求补充。

### 3.11 Step 10：当当前口径不符合预期时的推荐式确认（Recommended Scope Options）

当客户表示当前口径**不符合预期**时，agent 不应直接反问：

- “那你想要什么样的口径？”
- “你自己定义一下你要的口径。”

相反，agent 应基于客户已经表达出来的期待信息，主动给出**若干推荐口径选项**，帮助客户确认更接近哪一种。

#### 默认处理顺序
1. 先总结客户当前已经表达出来的期待；
2. 明确指出当前实现口径与客户期待之间的主要差异；
3. 基于现有信息，给出 2–3 个推荐口径选项；
4. 说明这些选项之间的主要区别；
5. 请客户确认哪一个更接近其真实需求；
6. 若这些选项都不合适，再继续细化。

#### 推荐选项的组织方式
推荐口径选项通常可围绕以下差异展开：
- 统计对象不同
- 纳入范围不同
- 排除逻辑不同
- 时间口径不同
- 主体粒度不同
- 当前实现口径 vs 业务状态口径不同

#### 推荐表达方式
agent 应尽量使用客户容易理解的话来描述选项，而不是直接堆砌产品术语。

例如可以表达为：
- 方案 A：按当前实现逻辑继续
- 方案 B：按“曾经满足过某条件的人”来统计
- 方案 C：按“在指定时间范围内首次满足条件的人”来统计

#### 硬性要求
- 不推荐直接要求客户完整定义目标口径；
- 若客户给出的期待信息仍不足以形成推荐选项，agent 再请求更具体的信息；
- 推荐选项应建立在当前证据和客户表述之上，不应凭空杜撰。

### 3.12 Step 11：沉淀可复用的口径确认结果（Reusable Scope Output）

当本轮口径确认达到可结束状态时，agent 应尽量输出一个可供后续分析直接复用的口径结论。

#### 该输出物应尽量包含
- 已定位的分析对象
- 当前统计对象
- 当前统计范围
- 当前筛选条件
- 当前分组方式
- 当前时间范围 / 时间粒度
- 当前计算方式
- 当前关键定义对象（如标签 / 分群 / 虚拟属性）的使用方式
- 已确认项
- 待确认项
- 若已确认，可写明“后续分析默认按此口径继续”

#### 输出物要求
- 该输出物不应只是泛泛解释；
- 应能作为后续任务的输入；
- 应尽量结构化，便于后续引用、转写或复用。

#### 该输出物可服务的后续任务
- SQL 改写
- 报告生成
- 结论复核
- 新分析设计
- 后续客户沟通

### 3.13 Step 12：确认是否进入后续动作（Downstream Gate）

口径确认完成后，agent 才能决定是否进入后续动作。

#### 可以进入后续动作的前提
至少满足以下之一：
- 客户明确表示当前解释已满足需求；
- 客户明确确认当前逻辑符合其业务口径；
- 双方已经明确当前不一致点，并确认后续要按哪个新口径继续。

#### 后续动作包括
- SQL 改写
- 新分析设计
- 报告生成
- 结论整理
- 优化建议输出

#### 若尚未确认
如果当前口径仍未确认：
- 不应直接输出依赖该口径的最终报告；
- 不应直接固化最终分析结论；
- 不应把客户预期直接写成既定事实。

### 3.14 信息不足时的默认决策（Insufficient Information Handling）

当信息不足以支持当前层级的判断或解释时，agent **必须先向客户请求补充信息**，而不是直接依赖猜测继续推进。

#### 默认处理顺序
1. 先判断当前缺少的是：
   - 对象定位信息
   - SQL / query
   - 定义层材料
   - 客户意图层级
2. **优先向客户请求补充信息**
3. 若客户无法提供、暂时拿不到、或无法明确说明，则**再尝试通过 ae-cli 命令补查**：
   - query
   - adhoc_query
   - report / dashboard 配置
   - 对象相关上下文
   - 其他可用于解释当前口径的材料
4. 若客户与 ae-cli 都无法提供足够信息，则只输出：
   - 初步解释
   - 待确认项
   - 推测项
   - 建议补充的信息

#### 硬性要求
- 不得在信息不足时伪装成已经完成高确定性口径确认；
- 不得在未获得足够证据时，把推测写成事实；
- 若客户不能继续提供信息，而 ae-cli 也无法可靠补查，则应明确说明当前只能停留在”初步解释 / 待确认状态”。

### 3.15 冲突与分歧时的决策方式（Conflict Resolution in Workflow）

若流程中出现冲突，必须显式拆开处理：

- 客户预期 vs 当前 SQL 实现
- 当前使用方式 vs 定义方式
- 展示时区 vs 结算时区
- 当前结果页刷新 vs 对象重算
- 当前 query 逻辑 vs 产品标准语义
- 客户说法 vs ae-cli 补查结果

处理步骤：
1. 分别陈述两边是什么
2. 说明当前证据支持哪一边
3. 若不能确认，标注待确认
4. 请求客户补充必要材料

### 3.16 默认结束条件（Default Exit Conditions）

在以下任一条件满足时，本轮 workflow 可视为完成：

- 客户明确表示当前解释已满足需求；
- 客户明确要求进入下一层；
- agent 已清楚说明当前仍缺什么信息，并等待客户补充；
- 当前只能给出初步解释，且已明确说明不能下最终结论；
- 已沉淀出可供下一步分析继续使用的口径确认结果；
- 口径已确认，任务进入下游阶段（如 SQL 改写 / 报告生成 / 新方案设计）。

## 5. 输入输出约定（I/O Contract）

本节定义本能力在输入、默认处理、信息不足处理与输出交付上的最低要求。  
本能力的输出不仅需要帮助客户理解当前口径，还必须能够作为下一步分析、SQL 改写、报告生成或结果复核的输入。

### 5.1 必要输入（Required Inputs）

本能力的输入分为两层：

#### A. 定位输入
用于确定当前要对齐的是哪个具体分析对象。可用输入包括：

- `project_id`
- `dashboard_id`
- `report_id`
- `SQL`
- `query / qp / adhoc_query`
- 历史分析结果原文 / 截图 / 链接

#### B. 解释输入
用于确定当前需要对齐什么内容。可用输入包括：

- 客户想确认的对象
- 客户最关心的问题点
- 是否只看当前实现，还是要下钻定义层

#### 5.1.1 必要输入的最低要求
如果已经具备以下任一类信息，则可以开始口径对齐：

- 可定位对象的 SQL / query / qp / adhoc_query
- 可定位对象的 `project_id / dashboard_id / report_id`
- 足以帮助系统进一步定位对象的历史分析结果原文 / 截图 / 链接

如果上述信息都缺失，则不能给出高确定性的最终口径结论，只能先请求定位信息。

#### 5.1.2 对“已开始”的理解
本能力允许在输入不完整时开始，但开始后必须根据当前证据层级控制输出深度：

- 若对象已定位且 SQL / query 逻辑可读，可进入 L1 当前实现层；
- 若对象未完全定位，只能做初步解释，不得伪装成已完成口径确认。

### 5.2 可选输入与默认处理（Optional Inputs and Defaults）

当可选输入缺失时，执行体应尽可能先基于已有信息推进到“当前可确认层”；  
只有在继续推进会显著影响口径判断时，才主动请求补充信息。

#### 5.2.1 对象定位输入缺失时的默认处理
- 如果客户直接提供了 `SQL`，默认先基于 SQL 解释当前实现口径。
- 如果客户未提供 SQL，但提供了 `project_id / dashboard_id / report_id`，默认先通过系统补查对应的 query / adhoc_query / 配置。
- 如果客户未提供完整定位信息，但提供了历史分析结果原文 / 截图 / 链接，则默认先尝试定位对象，或基于已有内容做初步解释。
- 如果仍无法定位对象，则只能输出：
  - 当前可确认内容
  - 待确认内容
  - 推测内容

#### 5.2.2 对齐层级未指定时的默认处理
- 如果客户没有说明要对齐到多细，默认只输出 **L1 当前实现层**。
- 不默认直接进入：
  - 标签 / 分群 / 虚拟属性 / 维度表属性定义层
  - 版本 / 时区 / 更新方式
  - 条件细节 / 序列规则 / 历史版本

#### 5.2.3 关键问题点未指定时的默认处理
如果客户没有明确说明最关心的问题点，默认先解释：

- 统计对象
- 统计范围
- 筛选
- 分组
- 时间
- 计算方式
- 当前对象在本查询中的使用方式

然后在第一轮输出后，再请示客户是否需要继续下钻。

#### 5.2.4 提供 SQL 时的默认处理
- 如果客户提供了 SQL，默认先解释 **SQL 所表达的当前统计逻辑**。
- 但不得默认认为：
  - SQL 的最终输出结构
  - 前端最终展示结果
  - 客户看到的图表 / 卡片 / 报表呈现  
  完全等价。

只有在以下情况下，才需要额外确认“前端最终展示结果”这一层：
- 客户明确提到前端展示结果与预期不符；
- 客户的问题明显在问：
  - 为什么前端是这个结果
  - 为什么图表 / 卡片 / 报表呈现与理解不一致
  - 为什么前端看起来和 SQL 逻辑理解不一致

#### 5.2.5 系统上下文的默认补全处理
- `dashboard / report / query` 上下文默认不作为向客户优先索取的信息。
- 默认客户通常无法直接提供这类上下文。
- 这类信息应由系统优先通过 ae-cli 补查。
- 如果系统能够补查到，则基于补查结果继续解释。
- 如果系统无法补查到足够信息，则基于当前已获得的信息先输出可确认内容，并明确哪些部分是推测。

#### 5.2.6 查询结果样例与前端截图的条件触发规则
- 查询结果样例不是默认必填输入。
- 前端截图也不是默认必填输入。
- 只有在以下情况下，才条件触发请求：
  - SQL 不能说明前端最终结果形态；
  - 客户明确质疑前端展示结果；
  - 当前争议点在结果呈现层，而不是底层统计逻辑。

### 5.3 输入不足时的处理（Behavior Under Insufficient Input）

当信息不足以支持高确定性口径判断时，执行体必须降级为“已确认部分 + 待确认部分 + 推测部分”的输出模式，而不得伪装成完整确认结论。

#### 5.3.1 信息不足的判定
以下任一情况均视为信息不足：

1. **对象未充分定位**
   - 没有 SQL
   - 没有足以定位对象的 `project_id / dashboard_id / report_id`
   - 系统补查后仍无足够对象上下文
   - 客户仅给出模糊问题，没有明确分析对象

2. **当前实现可读，但定义层证据不足**
   - SQL 能看懂当前统计逻辑
   - 但客户问的是标签 / 分群 / 虚拟属性 / 维度表属性本身的定义
   - 当前没有定义 SQL、配置截图、版本信息等证据

3. **关键判断依赖额外信息**
   - 粒度是否一致
   - 前端结果是否与 SQL 完全对应
   - 虚拟属性表达的是事件级条件还是用户级状态
   - 标签 / 分群当前是否为动态匹配还是历史版本

#### 5.3.2 信息不足时禁止行为
信息不足时，执行体不得：

- 把推测写成确定事实
- 把当前实现逻辑直接等同于客户期待的业务定义
- 因为客户给了 SQL，就假设前端结果与 SQL 完全一致
- 因为信息不足，就完全不输出任何可确认内容

#### 5.3.3 信息不足时的处理顺序
当信息不足时，应按以下顺序处理：

1. 先判断缺的是哪类信息：
   - 对象定位信息
   - 定义层信息
   - 输出结构信息
   - 版本 / 时区 / 配置细节

2. 判断基于已有信息能确认到哪一层：
   - 至少能否确认 L1 当前实现层
   - 还是只能做更初步的解释

3. 只在必要时请求客户补充信息

4. 如果客户无法补充，则由系统通过 ae-cli 补查

5. 如果仍不足，则输出降级结论：
   - 当前已确认内容
   - 当前待确认内容
   - 当前推测内容
   - 若继续确认还需要什么

#### 5.3.4 信息不足时的输出格式
信息不足时，输出至少应包含：

- **当前已确认**
- **当前未确认**
- **当前推测**
- **若继续确认，需要什么**

#### 5.3.5 推测标记规则
只要满足以下任一情况，就必须显式写出“这是推测”或同等表述：

- 对象尚未完全定位
- 定义层规则缺失
- 系统补查后仍未获得足够证据
- 当前判断依赖经验推断而非 SQL / 配置 / reference 明证
- 前端结果形态无法从 SQL 直接还原

#### 5.3.6 降级输出的最低允许程度
- 只要能定位到当前 SQL / query 的统计逻辑，就允许输出**部分 L1**；
- 但不得冒充已经进入 L2 / L3；
- 若连 L1 都无法确认，则只能输出对象层面的初步解释与待确认项。

### 5.4 输出约定（Output Contract）

输出必须同时满足两个目标：

1. **面向客户可读**
2. **面向后续任务可复用**

#### 5.4.1 输出层级要求
- **L1**：解释当前实现层；不得冒充已经进入 L2 / L3。
- **L2**：解释定义层来源；不得冒充已经验证完所有细节规则。
- **L3**：解释复杂规则与边界条件；允许细化到规则层。

输出层级必须与当前证据层级一致。

#### 5.4.2 输出内容要求
L1 当前实现层输出应覆盖预定义的关键口径项，包括但不限于：

- 统计对象
- 统计范围
- 筛选条件
- 分组方式
- 时间逻辑
- 计算方式
- 标签 / 分群 / 虚拟属性 / 维度表属性在当前查询中的使用方式

但并不是每一轮都一定能对每项给出“有内容的口径说明”。  
对于每一项，执行体都必须明确给出以下三种状态之一：

1. **已确认**
   - 当前信息足以解释该项口径；
2. **当前实现未使用**
   - 当前 SQL / query / 报表中本来就没有使用该项；
3. **暂无法确认**
   - 当前信息不足，无法对该项做出定论。

执行体不得将以下两种情况混为一谈：
- 当前实现未使用该项
- 当前信息不足，暂无法确认该项

也就是说，输出中不得静默跳过某一关键口径项不提。

#### 5.4.3 输出分类要求
输出必须清晰区分以下四类信息：

- **已确认**
- **待确认**
- **推测**
- **下一步建议**

#### 5.4.4 输出确认动作要求
只要本轮已经输出了口径说明，就必须追加确认动作，包括：

- 当前是否符合客户预期
- 若不符合，是否需要继续对齐更细部分
- 若继续下钻，需要补充什么信息
- 若当前口径不符合预期，可给出推荐口径选项

不得只反问客户“你想要什么口径”，而应先给当前解释，再给推荐选项。

#### 5.4.5 输出可复用性要求
输出不能只是一次性说明文，而必须能作为下一步分析任务的输入。  
输出至少应沉淀出以下类型的信息：

- 当前确认口径
- 当前未确认口径
- 当前争议点
- 推荐后续动作

这些内容后续应能够直接衔接到：
- SQL 改写
- 新分析方案设计
- 报告生成
- 结果复核
- 客户进一步确认

#### 5.4.6 输出形式要求
- 输出必须结构清晰；
- 但允许根据：
  - 当前层级
  - 客户熟悉度
  - 问题复杂度  
  灵活调整措辞；
- 内容结构应保持强约束，文本形式可适度灵活。

### 5.5 硬性约束（Hard Constraints）

- 若没有定位信息，也没有 SQL / query / 报表上下文，不得给高确定性口径结论。
- 若客户没有说明想对齐到多细，默认只输出 L1 当前实现层。
- 若输入不足，先请求客户补充；客户无法提供时，再由系统通过 ae-cli 补查。
- 每轮输出口径说明后，都必须请求客户确认是否符合预期。
- 若客户认为当前口径不符合预期，应给出推荐口径选项，而不是只反问客户。
- 最终输出必须可作为下一步分析输入复用。
- 输出必须明确区分：
  - 当前实现未使用
  - 当前暂无法确认
  - 当前已确认
- 任何依赖不完整证据的判断，都必须明确标记为“这是推测”或同等表述。

## 6. 规则与边界（Rules & Boundaries）

本节定义本能力在执行过程中必须遵守的规则、禁止行为、高风险口径点，以及与后续任务之间的边界。  
前文主要说明“应当如何做”，本节主要说明“哪些事绝对不能做、哪些情况下必须更谨慎、哪些边界不能越过”。

### 6.1 必须遵守的规则（Hard Rules）

#### 6.1.1 先定位对象，再解释口径
在对象尚未定位清楚前，只能给出初步解释，不得给出高确定性的最终口径结论。  
对象定位通常优先依赖：

- `SQL`
- `query / qp / adhoc_query`
- `project_id / dashboard_id / report_id`
- 或足以帮助系统继续定位的历史分析结果原文 / 截图 / 链接

#### 6.1.2 先解释当前实现层，再决定是否下钻
默认应先解释 **L1 当前实现层**。  
不得默认一开始就直接进入：

- 标签 / 分群 / 虚拟属性 / 维度表属性定义层
- 版本层
- 时区层
- 条件规则层
- 历史版本层

#### 6.1.3 SQL-first，但不能 SQL-only
`SQL` 是当前实现层的第一证据。  
但当问题涉及以下内容时，不能只依赖 SQL，必须结合 reference 文档与其他证据：

- 标签 / 分群 / 虚拟属性 / 维度表属性定义
- 版本
- 时区
- 更新方式
- 阶段值规则
- 条件型对象的复杂规则

#### 6.1.4 必须区分三种状态
在解释关键口径项时，必须明确区分以下三种状态：

1. **已确认**
2. **当前实现未使用**
3. **暂无法确认**

不得混淆：
- 当前实现未使用该项
- 当前信息不足，暂无法确认该项

#### 6.1.5 每轮输出口径说明后都要确认是否符合预期
只要本轮已经输出了口径说明，就必须追加确认动作，包括：

- 当前是否符合客户预期
- 是否需要继续下钻
- 若继续下钻，还缺什么信息

#### 6.1.6 若当前逻辑与客户预期可能不一致，必须指出“当前逻辑更像在判断什么”
当当前实现逻辑与客户自然语言中的业务理解可能不一致时，必须明确指出：

- 当前逻辑更像在判断什么
- 不完全等于客户口中的哪个业务状态
- 是否需要进一步对齐更细定义

#### 6.1.7 输出必须可供下一步分析复用
输出不能只是一次性说明文，而必须可用于后续任务，包括：

- SQL 改写
- 新分析方案设计
- 报告生成
- 结果复核
- 客户进一步确认

### 6.2 禁止行为（Prohibited Behaviors）

#### 6.2.1 不得把推测写成已确认事实
只要判断依赖不完整证据，就不得把其写成已确认事实。  
必须使用类似表达：

- 基于当前信息，较可能……
- 当前仍待确认……
- 如果当前采用的是……逻辑，则更可能……

#### 6.2.2 不得在对象未定位清楚时给高确定性结论
在缺少足够对象定位信息时，不得直接给出高确定性的最终口径结论。  
只能输出：

- 当前可确认内容
- 当前待确认内容
- 当前推测内容

#### 6.2.3 不得把当前实现逻辑直接等同于客户期待的业务定义
当客户使用业务语言提问，例如：

- 这是不是付费用户？
- 这是不是留存用户？
- 这是不是我想要的人群？

如果定义层尚未确认，不得直接顺着客户语言给出“是”的结论。

#### 6.2.4 不得把对象当前使用方式误当成对象本身定义方式
不得把对象在当前查询中的使用方式，误当成对象本身的定义方式。  
尤其对于以下对象：

- 标签
- 分群
- 虚拟属性
- 维度表属性

当前查询只能先说明它们在本次分析中如何被使用；  
若需确认其本身定义，必须进入定义层并基于额外证据判断。  
不得因为某对象当前被用于筛选、分组或计算，就直接断言这就是该对象本身的完整定义语义。

#### 6.2.5 不得把 SQL 当前输出形态直接等同于前端最终展示结果
即使客户提供了 SQL，也不得直接假设：

- SQL 的最终输出结构
- 前端最终展示结果
- 客户看到的图表 / 卡片 / 报表呈现

三者完全等价。

#### 6.2.6 不得静默跳过关键口径项
对于预定义的关键口径项，不得因为该项没有明确内容就直接跳过不提。  
每项都必须明确标明是：

- 已确认
- 当前实现未使用
- 暂无法确认

#### 6.2.7 不得混淆“当前实现未使用”与“当前无法确认”
不得把以下两种情况混写成同一个“没有”：

- 当前实现中本来就没有使用该项
- 当前信息不足，无法确认该项

#### 6.2.8 不得一开始就过度索取补充材料
不得在第一步就要求客户一次性提供大量补充材料，例如：

- SQL
- project_id
- dashboard_id
- report_id
- query 配置
- 结果样例
- 前端截图
- 定义 SQL
- 规则截图

应先基于已有信息推进到当前可确认层，只有在继续推进明显受阻时，才最小化地请求补充信息。

#### 6.2.9 不得在信息不足时只回复“请补充信息”而不先输出当前可确认内容
即使信息不足，也应先输出当前已能确认的部分，再说明缺口，而不是只给出补充请求。

#### 6.2.10 不得在口径未确认前直接推进下游任务结论
在当前口径尚未确认前，不得直接：

- 生成最终分析报告
- 输出高确定性的 SQL 改写结论
- 把当前结果写成最终业务结论
- 把推测定义写入正式分析结论

#### 6.2.11 不得对数据库中的数据或数据资产做任何直接修改
本能力仅用于：

- 查询与解读当前数据逻辑
- 对齐统计口径
- 提出新口径建议
- 给出查询层 / SQL 层调整建议

不得对以下对象做任何直接修改：

- 底层数据库数据
- 结果表
- 标签结果
- 分群结果
- 维度表
- 其他数据资产

即使客户表达了修改意图，本能力也不得将对数据本身的修改作为口径对齐过程的一部分执行。

### 6.3 推测与不确定性的处理（Handling Uncertainty and Inference）

#### 6.3.1 可以做推测的场景
只有当以下条件同时满足时，才允许做推测：

- 已有 SQL / query / 对象信息足以支持部分判断
- 但仍缺少某些定义层或展示层证据
- 且客户当前希望先得到一个初步方向

#### 6.3.2 推测必须如何表达
推测必须显式表达，不得伪装成已确认结论。  
推荐表达包括：

- 基于当前信息，较可能是……
- 当前仍待确认，但大致可能是……
- 如果当前对象采用的是……逻辑，则结果更可能表示……

#### 6.3.3 不能推测的场景
如果出现以下情况，则不能给具体推测，只能说明无法判断及所需信息：

- 连对象都未定位到
- 连当前实现层都无法看清
- 当前证据连部分 L1 都不足以支撑

### 6.4 超出范围时的处理（Out-of-Scope Handling）

#### 6.4.1 本能力的核心范围
本能力的核心范围包括：

- 对齐统计口径
- 解释当前实现
- 区分实现层与定义层
- 发现客户预期与当前逻辑的差异
- 给出推荐口径方向
- 为下游任务提供可复用的口径输入

#### 6.4.2 不属于本能力核心范围的任务
以下任务不属于本能力的核心职责：

- 直接修改底层数据
- 执行数据库写入 / 更新 / 删除
- 在未确认口径前直接生成最终分析结论
- 纯文案润色
- 不依赖对象与口径的泛泛业务咨询

#### 6.4.3 遇到超出范围任务时的处理
当客户请求超出本能力范围的任务时，应：

- 明确说明该任务不属于当前口径对齐范围
- 如果仍与口径相关，则先完成口径确认，再衔接后续任务
- 如果完全无关，则不强行套用本能力

### 6.5 高风险口径点（High-Risk Scope Triggers）

当以下高风险口径点出现时，执行体应默认采用更保守的解释策略，包括但不限于：

- 更明确地区分“当前实现”与“定义层语义”
- 更明确地区分“已确认”与“推测”
- 更谨慎地判断客户预期与当前逻辑是否一致
- 在必要时主动请示是否继续下钻

#### 6.5.1 标签 / 分群的使用层与定义层混淆
高风险原因：
- 当前查询里的筛选 / 分组使用方式，不等于对象本身定义；
- 客户容易把“当前怎么用”误解为“对象怎么定义”。

遇到该情况时，应优先：
- 先解释当前使用方式
- 再说明这不等于对象定义
- 若客户继续追问定义，再进入定义层

#### 6.5.2 虚拟属性表达式语义
高风险原因：
- 虚拟属性在技术上可能只是表达式结果；
- 客户却容易把它理解成完整业务状态。

特别需要谨慎的情形包括：

- 布尔判断
- 时间比较
- 首次 / 末次
- 是否完成某行为
- 用户状态 vs 事件条件

#### 6.5.3 事件级字段与用户级字段混用
高风险原因：
- 事件级字段与用户级字段混用会直接影响：
  - 人数
  - 主体数
  - 状态判断
  - 去重口径

遇到该情况时，应明确说明：
- 当前判断的是事件还是主体
- 当前去重键是什么
- 是否存在粒度不一致风险

#### 6.5.4 封装 SQL 与前端展示结果差异
高风险原因：
- SQL 可能表达的是原始逻辑、中间层结果或封装输出；
- 前端看到的图表 / 卡片 / 报表可能还经过进一步处理。

遇到该情况时，应：
- 先解释当前统计逻辑
- 不默认断言前端最终结果形态
- 只有当客户明确提及前端结果与预期不符时，再请示是否要对齐前端展示层

#### 6.5.5 版本 / 时区 / 更新方式
高风险原因：
- 以下因素一旦与客户问题有关，会直接影响口径：
  - 标签日期版本
  - 动态匹配
  - 历史版本
  - 结算时区
  - 展示时区
  - 自动 / 手动 / 编辑后更新方式

遇到“为什么和以前不一样”“为什么时间对不上”等问题时，应自动提高谨慎级别。

#### 6.5.6 阶段值
高风险原因：
- 阶段值容易被误解释成：
  - 日均
  - 简单平均
  - 每日相加
- 实际上可能是：
  - 阶段总和
  - 加权平均
  - 不完整数据剔除后的结果

遇到阶段值时，应优先参考：
- `stage-value-logic-explanation.md`

#### 6.5.7 “没有”到底是哪种没有
高风险原因：
- 很容易把“当前实现未使用”误写成“当前无法确认”
- 或把“当前无法确认”误写成“当前没有”

遇到任何“没有”的情况时，都应先判断：
- 是实现上没有
- 还是证据不足

#### 6.5.8 客户把技术字段当成业务状态
高风险原因：
- 客户常会直接把技术对象理解成业务对象，例如：
  - 某虚拟属性 = 某类用户
  - 某标签值 = 高价值用户
  - 某分群命中 = 某业务状态成立

遇到该情况时，应：
- 先解释当前逻辑更像在判断什么
- 再请示这是否符合客户想要的业务口径
- 必要时给推荐口径选项，而不是直接顺着客户说法确认

### 6.6 与后续任务的边界（Boundary with Downstream Tasks）

#### 6.6.1 本能力通常作为后续任务的前置步骤
本能力通常作为以下任务的前置步骤：

- SQL 改写
- 新分析方案设计
- 报告生成
- 结果复核
- 客户进一步沟通

#### 6.6.2 进入后续任务前的要求
如果当前口径仍未确认清楚，则：

- 不应直接生成最终分析结论
- 不应直接给高确定性的 SQL 改写建议
- 不应把推测定义写入报告正文

#### 6.6.3 合理的衔接方式
当前能力完成后，可将结果沉淀为：

- 当前确认口径
- 当前未确认点
- 推荐新口径方向
- 后续所需补充信息

然后再交给后续任务继续处理。
