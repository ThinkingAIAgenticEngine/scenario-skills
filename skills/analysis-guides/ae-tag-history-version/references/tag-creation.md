# Tag Creation Flow (used when the customer has not provided a tag)

> **Entry condition**: The customer has only described a business need (e.g., "I want to tag users by XX") and there is no existing tag available.
> **On completion**: The tag has been created and verified successfully; return to Step 0 of SKILL.md Part Two and continue the history version update flow.

## Product Skill dependency

Before composing or executing a tag creation command, locate the `ae-analysis` product Skill using [Execution Prerequisites and Product References](../SKILL.md#execution-prerequisites-and-product-references). Read `references/user_tag_create.md`, `references/user_tag_models.md`, and `references/audience_models.md` relative to the resolved product Skill root. These files belong to `ae-analysis`; they are not bundled with this scenario Skill. If the dependency or a required reference is missing, report what is unavailable and request that the product Skill be made available before creating the tag. Do not guess a definition schema or a repository-specific installed path.

## Step 1: Confirm the tag creation requirement (mandatory)

**Fixed question template (use verbatim, no improvisation)**: When the customer has not described the tagging requirement, you must use the following original text when asking the customer (only conversion into the language of the customer's question is allowed; the format and structure must remain unchanged; do not rewrite, reorganize, add to, or remove it):

> Before creating a tag for you, I need you to describe the tag content, for example, creating the level property value at the time of the user's last triggered level_up event over the "past 7 days", or the "total count of payment behaviors in the last 30 days", and similar requirements.

**The customer describes the requirement in natural language; the Agent determines and lists the configuration**:

1. **Confirm only 2 core elements with the customer** (they must be provided or confirmed by the customer; do not decide on your own; ask until it is clear):
   - **Analysis metric**: what behavior/event/property the tagging is based on, and what value is taken.
   - **Analysis period**: the time range the tagging rule is based on; **it must be dynamic time** (a relative/rolling time window, e.g., "last 30 days", "past 7 days"); static time (a fixed date range, e.g., 2026-09-01 ~ 2026-09-30) does not involve history version needs and is not applicable to this flow; when the customer proposes static time, guide them to use dynamic time instead.

   Any element other than these (tag name, creation type, tag value type, time zone, etc.) must **never be asked back to the customer**.
2. **Scan on demand**: once the core elements are clear, scan the metadata (events, properties) based on the customer's description, verify that the behaviors/events/properties mentioned by the customer actually exist, and confirm the exact event names and property names.
3. **The Agent determines and lists the configuration on its own** (combining the customer's needs and the metadata verification results; decide directly; do not ask the customer):
   - **Creation type**: determined by the Agent (first/last-event rule, SQL rule, etc.).
   - **Tag name**: generated by the Agent; the customer does not need to provide it:
     - `display_name`: a human-readable display name (≤80 characters)
     - `tag_name`: letters, digits, and underscores only, starting with a letter, ≤80 characters (e.g., `tag_login_gap_20261104`)
   - **Tag value type**: e.g., `datetime`, `string`, numeric, etc. (matching the tagging rule).
   - **Time zone**: the time zone used for the tagging calculation; handle it according to the current project's time zone configuration (`--zone-offset`); do not guess and do not ask the customer.
4. After listing the final configuration above to the customer, execute the creation directly; item-by-item confirmation from the customer is not required (as long as the core analysis metric and analysis period have been confirmed).

**Default configurations that do not require asking the customer** (required for the history version application, enabled by default):

- **Auto-update**: enabled by default; the refresh time **defaults to 3:00 AM** (replaced only when the customer explicitly specifies another time).
- **Auto-backup**: a platform asset-level default behavior (the data foundation of tag history versions); keep it enabled by default.

## Step 2: Create the tag

```bash
ae-cli analysis user-tag create --project-id <project_id> \
  --tag-name <new_tag_name> \
  --display-name "<display name>" \
  --definition-request '<semantic snake_case tag definition>' \
  --enable-auto-refresh true \
  --auto-refresh-schedule '{"frequency":"daily","time":"03:00"}'
```

- `--definition-request`: the semantic tag definition; fields use **snake_case**. Use `references/user_tag_models.md` for the model structure and `references/audience_models.md` for shared primitives, both relative to the resolved `ae-analysis` product Skill root described above.
- **Write the analysis period into the definition as dynamic time** (e.g., `{"mode":"recent","unit":"day","value":30}`); do not write a fixed date range; static time does not involve history version needs.
- **Auto-update is enabled by default (3:00 AM)**: the creation command includes `--enable-auto-refresh true` and the refresh schedule by default; schedule and cron are mutually exclusive, choose one:
  - `--auto-refresh-schedule '{"frequency":"daily","time":"03:00"}'` (default)
  - `--auto-refresh-cron '0 0 3 * * ?'` (Quartz cron, based on the tag time zone)
  - Replace it only when the customer explicitly specifies another time (e.g., every Monday at 04:30: `{"frequency":"weekly","time":"04:30","weekdays":[1]}`)
- **Auto-backup remains enabled by default**; no extra operation is needed at creation; only when the customer explicitly asks to disable it, run `ae-cli analysis-governance asset batch-disable-auto-backup --project-id <project_id> --node-ids '[<asset node ID>]'` (a write operation; confirm with the customer before executing), and inform the customer that disabling it will affect the history version generation of that tag.
- Handle time zone related needs according to the current project's time zone configuration (`--zone-offset`); do not guess.

## Step 3: Verify the creation result

```bash
ae-cli analysis user-tag get --tag-names '["<tag_name>"]'
```

- **Successful submission is not the same as completed creation**: a successful return from `create` only means the task has been submitted; the initial calculation is triggered automatically, and **you must not call `user-tag refresh` after creation**.
- Poll `get` until `progress=100` and both `refresh_time` and `users_num` are returned; only then is the creation successful.
- Polling cadence: once every 10–30 seconds, for at most several minutes; if it is still incomplete, tell the customer the task has been submitted and to check again later.
- After verification passes, report the `tag_name` (the exact identifier) and `users_num` to the customer, then return to SKILL.md Part Two Step 0.

## ⛔ Prohibitions

1. DO NOT fabricate `tag_name`, tagging rules, or creation results; everything is subject to the actual command output.
2. DO NOT create a tag directly before the customer has provided or confirmed the core analysis metric (what behavior/event/property the tagging is based on, and what value is taken) and the analysis period.
3. DO NOT ask the customer to provide the tag name, creation type, tag value type, or time zone; these elements are determined by the Agent and listed in the reply.
4. DO NOT scan the metadata (events/properties) and preset tagging rules for the customer before the core elements (analysis metric, analysis period) are clear.
5. DO NOT report "task submitted" as "tag created"; you must verify `progress=100` and that `users_num` is present.
6. DO NOT let the Agent decide the analysis period on its own; the analysis period must be provided or confirmed by the customer, and it must be dynamic time (a relative time window); static time (a fixed date range) must not be used.
7. **Auto-update and auto-backup are enabled by default; there is no need to ask the customer**; disable them only when the customer explicitly requests it, and first explain to the customer the impact on history versions.
8. DO NOT improvise or rewrite the question content when collecting tagging requirements from the customer; you must use the original text of the fixed question template in Step 1 (only conversion into the language of the customer's question is allowed).
