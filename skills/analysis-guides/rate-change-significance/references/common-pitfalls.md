## Common Pitfalls

| Pitfall | Wrong Approach | Correct Approach |
|---|---|---|
| Confusing this with rate-calculation auditing | Running retention-verification flow when the user only wants significance | Use this skill only for "is the change real" questions; redirect to `retention-verification` only when data correctness is in doubt (retention scenario only) |
| Using first_occurrence for a paired-design business question | For "the same subscribers active in BOTH periods", running first_occurrence and an independent Z-test | Detect phrasing that expresses **same users in both periods** semantics (any language — e.g. EN "same users in both periods", 中文 "同一批用户 / 两期都在", JP "両期間の同一ユーザー", KR "양 기간 동일 사용자") and use `paired` + McNemar. Phrasing expressing only **existing/old-user status** (e.g. EN "existing users", 中文 "老用户", JP "既存ユーザー", KR "기존 사용자") is an eligibility condition only and defaults to `period_active` for ordinary two-period comparison. |
| Using paired design for a first-occurrence business question | For "new users registered in July vs August", running the paired path because "active users" was mentioned | Detect **first-time / newly-acquired entry** semantics (any language — e.g. EN "new users / first order", 中文 "新用户 / 首单", JP "新規 / 初回", KR "신규 / 첫") in Step 1 and use `cohort_design=first_occurrence` + Template 2A; paired design on new users is degenerate (no overlap) |
| Using first_occurrence for "all visitors" with recurring cohort event | For "all visitors' 1-day conversion rate before vs after", using first_occurrence with cohort=page_view — this only counts users whose first-ever visit was in this period, excluding returning visitors | Detect **full active population this period** semantics (any language — e.g. EN "all visitors", 中文 "所有访客", JP "すべての訪問者", KR "전체 방문자") + recurring cohort event in Step 1 and use `cohort_design=period_active` + Template 2C-period-active; this includes all users who did the cohort event in this period |
| Using paired design for "all visitors" question | For "all visitors' conversion rate before vs after", using paired because "visitors" was mentioned — this excludes new visitors and churned visitors, changing the business question | Detect **full active population** semantics and use `period_active`. Only phrasing expressing **same users in both periods** semantics (e.g. EN "same visitors in both periods", 中文 "两期都访问", JP "両期間にアクセスする同一訪問者", KR "양 기간 모두 방문한 동일 방문자") justifies paired; phrasing expressing only old-visitor status does not. |
| Using period_active without checking overlap | Running period_active + independent Z silently when overlap is 70% (e.g., mostly the same active users in both periods) | Always compute and report the overlap_rate in Part 2; if ≥ 30%, recommend rerunning with `cohort_design=paired` for a precise McNemar test on the same users |
| Treating overlapping users as independent | Ignoring overlap, always using Z-test | For `first_occurrence`, overlap is structurally 0 so Z-test is correct. For `period_active`, overlap may be high (≥30%) — always compute and report the overlap rate in Part 2; if ≥30%, warn that independence is materially violated and recommend rerunning with `cohort_design=paired` for a precise McNemar test. If the user supplies CSV with paired users observed in both periods, route through Step 4c McNemar — do NOT attempt McNemar via first_occurrence/period_active SQL templates, they cannot produce matched pairs. |
| Declaring success on significance alone | "p < 0.05, so the change is a win" | Always pair significance with effect size and scenario-specific long-term metrics |
| Guessing event names | Hardcoding `register`/`login` without confirming | Ask the user once when event names are uncertain; use scenario presets only as defaults |
| Wrong time semantics | Mixing a rolling last-N-days window (any language — e.g. EN "last 7 days", 中文 "最近 7 天", JP "過去 7 日間", KR "최근 7일", includes today) with a fixed calendar window like "2026-07-01 ~ 2026-07-07" without stating which | State the window definition explicitly; for fixed-date cohorts use `BETWEEN '<START>' AND '<END>'` against `$part_date`; for rolling windows use the ae-analysis rolling-range helper and confirm whether "today" is included |
| Skipping power analysis | Concluding "not significant" and stopping | Always report whether the sample was large enough to detect the observed difference |
| Using retention ad-hoc for non-retention scenarios | Calling `model-type retention` with `first_order`/`purchase` | Use Step 2a-2 SQL path for repurchase/conversion/renewal/custom scenarios |
| Skipping SRM check | Running the test on unequal group sizes without checking | Always read the `srm_decision` block from `analyze.py` output; if `decision == "hard_reject"`, stop and surface the `reason` in Part 1 before testing. `skip` (paired) and `proceed_with_warning` (pre/post drift, or period_active with overlap) do not stop the test — surface the reason in Part 2. |
| Multiple comparisons | Running this skill on many metrics or many segments and reporting any p<0.05 as a real effect | Out of scope for this skill — apply Bonferroni/Benjamini-Hochberg correction across the family of tests, or restrict to a single pre-registered comparison |
| Misreading paired design as representative of the full population | "Paired test is significant, so the change applies to all users" | Paired design only includes users active in both periods; explicitly state the survivorship caveat in Part 5 |
| Hardcoding within-window for paired path | Always running 2B-paired-window even when the project uses exact-day retention | Pick the paired variant using the same scenario rule as first_occurrence (Step 2b-1 "Choosing the variant at runtime"); 2B-paired-exact for retention with exact-day definition, 2B-paired-window otherwise. Using a different variant than first_occurrence makes the two designs test different quantities. |
| Using period-level windows in paired SQL | `e."$part_date" BETWEEN '<A_START>' AND date_add('day', N, date('<A_END>'))` — tests "outcome anywhere in the period plus N days" instead of "outcome within N days of the user's cohort date" | Use per-user cohort-relative windows: compute `min("$part_date")` per user per period as the cohort date, then predicate outcome on `e."$part_date" > p.a_cohort_date AND e."$part_date" <= date_add('day', N, date(p.a_cohort_date))`. Otherwise the paired path tests a different quantity than the first_occurrence path. |


## Additional contract pitfalls

| Pitfall | Wrong Approach | Correct Approach |
|---|---|---|
| Filter mentioned but no SQL injection point | Mention `cohort_filter`/`outcome_filter` in prose and let the agent improvise placement | Use the exact `<<COHORT_FILTER>>` / `<<OUTCOME_FILTER>>` positions and alias rules in `sql-patterns.md`; omit the full placeholder line when empty |
| Replacing an exact template with “same structure” | Reconstruct 2A-window/2B-exact/2B-window/2C variants from memory | Use the fully documented template family; changing the date predicate can change the metric itself |
| Manual calculation when script exists | LLM hand-computes p-values by default | Use `analyze.py`; formulas are fallback/spec only and fallback output must be labeled |
| Mixing test logs into business report | Add version/test diagnostics to Part 1-7 | Keep production report contract unchanged; write regression notes to `test-log.md` |

| Treating existing/old-user status as automatically paired | `老用户 → paired` (any language — e.g. EN "existing users → paired", 中文 "老用户 → paired", JP "既存ユーザー → paired", KR "기존 사용자 → paired") | Treat old-user status as eligibility. Ordinary A/B old-user retention uses `register<A_START` for A and `register<B_START` for B plus period_active; only phrasing expressing **same old users in both periods** (e.g. EN "same old users in both periods", 中文 "同一批老用户", JP "両期間の同一の既存ユーザー", KR "양 기간 동일한 기존 사용자") uses paired with eligibility frozen at `register<A_START`. |
| Using Fisher for paired outcomes | Running Fisher on matched before/after a/b/c/d | Use McNemar; when `b+c<25`, use exact McNemar/binomial. |
| Blocking all n<30 samples | Refusing Fisher because a group has fewer than 30 users | Treat n<30 as a precision warning. Fisher exact remains valid for sparse independent tables. |
